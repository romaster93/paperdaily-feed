1.2 연구 목표 (Research Objective)

범용 서비스 로봇이 실제로 쓸모 있으려면 두 종류의 일반성을 동시에 만족해야 한다. 하나는 과제 일반성(task generality) — "저 농구공을 찾아줘", "프린터에 들렀다가 쓰레기통으로 가", "앉아서 쉴 곳을 찾아줘" 같은 임의의 자연어 요청을 처리하는 능력이다. 다른 하나는 장면 일반성(scene generality) — 사전 지도나 미세조정 없이 처음 보는 환경에서 즉시 동작하는 능력이다. 기존 VLN/ObjectNav 접근은 이 둘을 대체로 학습으로 획득한다. 즉 대규모 항해 데이터로 멀티모달 대형언어모델(MLLM)이나 전용 정책을 미세조정(fine-tuning)하여 "지시→저수준 액션" 매핑을 직접 학습시킨다. 그러나 이 경로는 (1) 과제 분포를 벗어나면 급격히 무너지고(demand-driven·multi-object처럼 조합적 과제에서 특히), (2) MLLM을 항해 전용으로 미세조정하면 원래 갖고 있던 범용 추론·상식 능력이 손상되며, (3) 새 장면·새 로봇·새 센서마다 재학습 비용이 든다.

SuperNav는 정반대 설계 철학을 취한다. MLLM을 항해 전용으로 전혀 미세조정하지 않는다. 대신 동결된 범용 MLLM에게 (a) 물리적 상호작용을 수행하는 에이전트 지향 도구(agent-oriented tools) 모음과, (b) 의사결정을 운동으로 번역하는 통합 시각-점 인터페이스(unified visual-point interface) 를 장착한다. MLLM은 요청 해석·관측 이해·다음 행동 추론이라는 자신의 본래 능력을 그대로 발휘하면서, "이미지 위의 어느 점으로 가라"는 고수준 결정만 내리고, 저수준 운동은 교체 가능한 실행기(executor)가 담당한다. 이로써 단일 시스템이 재학습 없이 instance-level / multi-object / demand-driven / category-level 항해를 전부 처리하는 것이 본 논문의 목표다.

2. 문제 정의 (Problem Definition)

2.1 도전과제 (Challenges)

(C1) 과제 일반성과 장면 일반성의 동시 달성. 전용 정책은 특정 과제 분포(예: ObjectNav 단일 객체)에 과적합되어, 순서 있는 multi-object나 수요 기반(demand-driven) 과제처럼 조합적·장기지평 요청에서 무너진다. 본 논문 Table 1이 이를 극명하게 보여준다 — StreamVLN은 단일 객체에서 SR 13.33%인데 multi-object에서는 SR 0.00% 로 완전히 붕괴한다.

(C2) MLLM 미세조정의 능력 손상. MLLM을 항해 액션 공간으로 미세조정하면 항해 성능은 오를 수 있으나, 임의 자연어 요청을 해석하고 상식적으로 추론하는 범용 능력이 희생된다. 이는 "any task"라는 목표와 근본적으로 상충한다.

(C3) 의사결정과 운동의 인터페이스 병목. MLLM이 자연어로 "앞으로 2m 가"라고 말하게 하면 기하 정합이 깨지고, 반대로 저수준 연속 액션을 직접 토큰으로 뱉게 하면 미세조정이 불가피하다. 고수준 의미 결정과 저수준 기하 실행을 깨끗하게 분리하면서도 둘을 연결하는 인터페이스가 필요하다.

(C4) 장기지평 컨텍스트 폭발. 에이전트 루프가 매 스텝 네 방향 RGB를 받아 누적하면, 수십~수백 스텝 뒤 이미지 컨텍스트가 폭발하여 MLLM 호출 비용·지연·환각이 급증한다. 어떤 정보를 보존하고 어떤 미디어를 버릴지 결정하는 컨텍스트 관리가 필수적이다.

(C5) 실패·막힘으로부터의 복구. 처음 보는 장면에서는 통로가 막히거나 후보가 오탐될 수 있다. 조밀한 재학습 없이 언제 경로를 바꾸고(recovery), 언제 목표 도달을 확정(completion) 할지 판단하는 절차적 지식이 필요하다.

2.2 핵심 해결책

SuperNav는 "동결 MLLM + 에이전트 하네스" 구조로 위 과제를 분해한다.

  1. 통합 시각-점 인터페이스 PointNav(d,[u,v]) (C3): MLLM이 네 방향 관측 이미지 중 하나(d)를 고르고 그 안의 정규화 좌표 [u,v]∈[0,1]²에 목적지를 직접 찍는다. 운동은 실행기가 내부에서 수행하고 새 네 방향 이미지·실행 상태·간결한 진단을 반환한다.
  2. 교체 가능한 두 운동 백엔드 (C1·C2): Geo-based Executor(깊이·캘리브레이션·포즈로 기하 실행)와 Learned Executor(DINOv2+flow 액션 헤드). MLLM은 둘 중 어느 것과도 동일 인터페이스로 대화하므로, 운동 능력은 학습으로 갈아끼우되 의미 결정은 미세조정 없는 범용 MLLM이 유지한다.
  3. 에이전트 지향 도구 + 항해 스킬(Markdown) (C5): search/recovery/completion 세 재발 결정에 대한 절차적 가이드를 Markdown 패키지로 제공하여, 재학습 없이 탐색·복구·완료 판단을 구조화한다.
  4. 과제-진행 및 컨텍스트 관리 (C4): 목표 레코드(pending/completed)·텍스트 상호작용 이력을 보존하되, 이미 처리되어 최신 관측으로 대체된 이미지의 미디어 페이로드만 제거(media-only pruning)하여 컨텍스트를 통제한다.

3. 핵심 방법론 (Core Methods)

3.1 통합 시각-점 인터페이스 (Unified Visual-Point Interface)

SuperNav의 심장은 의사결정과 운동을 잇는 단일 인터페이스다. 정의는 다음과 같다.

PointNav(d, [u, v]),   u, v ∈ [0, 1]
  d        : 어느 뷰(view)인지 식별 (front / right / back / left)
  [u, v]   : 해당 뷰 이미지의 좌상단(top-left) 기준 정규화 가로·세로 좌표

매 의사결정 사이클에서 로봇은 로봇 헤딩 기준 네 방향 RGB 이미지(front·right·back·left로 라벨)를 관측한다. MLLM은 이 네 장을 보고 "어느 뷰의 어느 픽셀로 가야 하는가"를 고른 뒤 PointNav(d,[u,v]) 한 번을 호출한다. 그러면 도구가 내부적으로 이동을 실행하고, 새 네 방향 이미지 + 실행 상태(성공/막힘) + 간결한 진단을 돌려준다.

이 설계의 의의는 세 가지다.

(1) 미세조정 제거. MLLM은 연속 액션(선속도·각속도)을 토큰으로 생성하지 않는다. 오직 "이미지 위의 점"이라는, 사전학습된 MLLM이 이미 잘 다루는 시각적 접지(visual grounding) 형식으로만 결정을 표현한다. 따라서 항해 전용 미세조정이 불필요하다.

(2) 방향 전환의 암묵적 처리. 네 방향 뷰를 모두 제공하므로, 뒤쪽 목표로 가려면 MLLM은 그냥 back 뷰의 점을 찍으면 된다. 명시적 "turn" 호출을 거의 쓰지 않아도 된다. 아블레이션(Table 6)이 이 효과를 정량화한다 — 전방 단일 뷰(front-only)로 제한하면 에피소드당 명시적 회전이 17.56회로 폭증하지만, 네 방향 전체 인터페이스에서는 0.41회에 불과하다.

(3) 피드백 기반 결정 수정. 실행 상태·진단이 다음 관측과 함께 돌아오므로, MLLM은 막힌 통로를 감지하면 경로를 수정할 수 있다. 결정과 실행이 폐루프로 묶인다.

ASCII로 한 의사결정 사이클을 나타내면:

   ┌─────────────────────────────────────────────┐
   │  관측: 네 방향 RGB  [front][right][back][left] │
   │        + 실행 상태 + 진단 + 목표/이력 레코드    │
   └───────────────────────┬─────────────────────┘
                           │  (동결 MLLM: 요청 해석·추론)
                           ▼
            결정:  PointNav(d=back, [u=0.62, v=0.55])
                           │
                           ▼
            실행기(Geo 또는 Learned)가 내부 이동 수행
                           │
                           ▼
            새 네 방향 이미지 + 상태 + 진단 반환 ──► (루프 반복)

3.2 두 운동 백엔드 (Interchangeable Motion Backends)

PointNav의 [u,v] 점을 실제 로봇 운동으로 바꾸는 실행기는 두 가지가 교체 가능하다. 인터페이스가 동일하므로 MLLM 측 코드는 전혀 바뀌지 않는다.

(A) Geo-based Executor (기하 기반 실행기). 깊이(depth)·카메라 캘리브레이션·포즈를 이용해 선택된 이미지 점을 환경 상의 실제 위치로 역투영한 뒤, 도달 가능한 목표까지 경로를 계획·추종한다. 내부적으로 Recast/Detour 기반 PathFinder로 navmesh 경로를 찾고 GreedyGeodesicFollower로 추종한다. 즉 고전적·결정론적 기하 파이프라인이다.

주요 상수(기본값):

standoff                    = 0.70 m   (목표 앞에서 멈추는 여유 거리)
candidate snap-distance 한계 = 0.75 m   (선택 점을 도달가능 지점으로 스냅)
follower goal radius        = 0.30 m   (도달 판정 반경)
follower steps              = 200       (추종 최대 스텝)

(B) Learned Executor (학습 기반 실행기). 목적지를 "목표 이미지"가 아니라 참조 관측 안에 찍힌 점(marked point) 으로 대체한다. 선택된 이미지–점 쌍과 최근 RGB 관측열로부터 국소 변위 증분(local displacement increments)과 정지 신호(stop) 를 예측한다. 인코더는 DINOv2, 입력은 가변 길이 시각 이력(variable-length visual history), 출력은 flow 액션 헤드가 담당한다.

실행 상수:

visual history limit = 12 observations  (stride-2 서브샘플 + 현재 프레임)
displacement 증분     = 8개의 2D 변위, 각 0.25 m
stop 임계            = pt ≥ 0.1 이 연속 2회 이상의 재계획에서 성립할 때 정지
motion primitives     = 10° 회전 + 0.25 m 전진

학습 설정(Learned Executor):

updates        = 45,000
global batch   = 256
optimizer      = AdamW
lr(policy)     = 1e-4,   lr(visual backbone) = 1e-5
weight decay   = 1e-6
schedule       = 500 warmup → cosine decay

손실은 flow matching 손실과 정지·잔여 항의 가중합이다.

ℒ_flow = (1/16) · E[ ‖ v_θ(x_τ, τ, c_t) − (ε − A) ‖²_F ]
ℒ_total = ℒ_flow + 0.5·ℒ_stop + 0.002·ℒ_remaining

여기서 v_θ는 flow 속도장 예측, x_τ는 노이즈 보간 상태, c_t는 이미지–점·이력 조건, A는 타깃 액션, ε는 노이즈다. ℒ_stop은 정지 분류, ℒ_remaining은 잔여 진행 추정을 보조한다.

설계적 함의. 두 실행기는 성능 프로파일이 다르다. Geo 실행기는 완전한 기하 정보(깊이·포즈)를 쓰므로 SPL이 월등히 높다(예: 단일 객체 0.4127 vs Learned 0.2059 — 거의 2배). Learned 실행기는 깊이·캘리브레이션 없이 RGB+점만으로 동작하므로 센서 요구가 낮지만 경로 효율이 떨어진다. 중요한 점은 SR(성공률)은 둘이 비슷하다는 것이다(multi-object에서 둘 다 34.00%). 즉 "어디로 갈지"의 의미 결정은 MLLM이 동일하게 내리고, "얼마나 잘 가는지"의 효율만 실행기 성질에 좌우된다. 이는 §1.2의 분리 철학을 실험적으로 입증한다.

3.3 에이전트 지향 도구와 항해 스킬 (Agent-oriented Tools & Navigation Skills)

SuperNav의 MLLM은 자유 서술이 아니라 도구 호출로 세상과 상호작용한다. 도구 모음은:

• initialization  : 세션 개시, 첫 관측 반환
• observation     : 현재 네 방향 관측 요청
• turning         : 명시적 회전 (드물게 사용)
• visual-point nav: PointNav(d,[u,v]) — 핵심 이동
• goal-progress   : 목표 레코드(pending/completed) 갱신
• termination     : 요청 충족/막힘 판단 후 루프 종료

여기에 항해 스킬(Navigation Skills) 이 얹힌다. 각 스킬은 "적용 상황 / 점검할 증거 / 권장 절차 / 연결 참조" 를 담은 Markdown 패키지로, MLLM이 재발하는 세 결정을 체계적으로 내리도록 절차적 지식을 주입한다.

┌──────────────┬───────────────────────────────────────────┐
│ Skill        │ 역할                                        │
├──────────────┼───────────────────────────────────────────┤
│ Search 가이드 │ 점검한 영역·보이는 개구부(통로)를 기록        │
│ Recovery 가이드│ 운동 실패 후 경로를 바꾸는 절차              │
│ Completion    │ 후보 외형 점검 + 검증된 목표 기록·정지 판단   │
│ 가이드        │                                            │
└──────────────┴───────────────────────────────────────────┘

왜 미세조정 대신 Markdown인가. 이 절차적 지식은 가중치가 아니라 텍스트 컨텍스트로 주입되므로, 새 과제·새 장면에 맞춰 스킬 문서를 추가·수정하는 것만으로 행동을 확장할 수 있다. 가중치를 건드리지 않으니 MLLM의 범용 능력(C2)이 보존된다. 아블레이션에서 스킬 제거가 가장 큰 성능 하락을 유발한다는 점(§5.5)이 이 설계의 핵심성을 뒷받침한다.

3.4 과제-진행 및 컨텍스트 관리 (Task-Progress & Context Management)

장기지평 에이전트 루프의 치명적 병목은 이미지 컨텍스트 폭발(C4)이다. SuperNav의 하네스는 다음을 유지·정리한다.

보존하는 것:

  • 목표 레코드(goal records): pending/completed 항목 추적 (multi-object·demand-driven의 순서 보장에 필수)
  • 텍스트 상호작용 이력: 점검한 영역·후보 단서·실패 시도를 텍스트로 보존
  • 이미지 경로(image paths): 미디어는 지워도 어떤 이미지가 있었는지 경로는 유지

버리는 것 (media-only pruning):

"성장하는 이미지 컨텍스트를 통제하기 위해, 하네스는 한 이미지가 처리되고 더 새로운 관측으로 대체(superseded) 되면 이후 요청에서 그 이미지의 미디어 페이로드를 제거한다."

즉 텍스트 이력·과제 상태·이미지 경로는 보존하되, 오래된 이미지의 실제 픽셀 데이터만 제거한다. 이로써 MLLM은 "무엇을 했고 무엇이 남았는지"의 서사적 맥락을 잃지 않으면서도 토큰 예산을 통제한다.

종료 판단. MLLM은 관측과 진행 레코드로부터 요청이 충족되었는지 혹은 실행이 막혔는지 스스로 판단하고, termination 도구를 호출해 루프를 끝낸다. demand-driven처럼 1~8단계가 순서대로 있는 과제에서는 각 단계 완료를 goal-progress에 기록하며 진행한다.

3.5 워크드 예제 — PointNav 한 사이클 (Worked Example)

인터페이스·백엔드·스킬이 실제 한 스텝에서 어떻게 맞물리는지 구체적 시나리오로 추적한다. 과제: "냉장고를 찾아라" (instance object navigation).

[t=0] 초기화
  init 도구 → 4-뷰 획득:
    front : 복도 끝, 희미한 금속 표면(냉장고 후보?) u≈0.52, v≈0.38
    right : 벽
    back  : 출발 지점(소파)
    left  : 주방 입구로 보이는 어두운 통로
  MLLM 추론: "주방이 냉장고 확률 높음 → left 통로 우선 진입"

[t=1] 탐색 스킬(search package) 활성
  MLLM이 PointNav(d=left, [u,v]=[0.50, 0.55]) 호출
    → left 뷰 하단 중앙(바닥 지점) = 통로 진입 waypoint
  Geo-based Executor:
    (1) [u,v]→깊이 역투영→카메라좌표 3D 점 p_cam
    (2) p_cam→월드좌표 p_world, 내비메시에 snap(0.75m 이내)
    (3) Recast/Detour PathFinder로 측지 경로 계산
    (4) GreedyGeodesicFollower로 standoff 0.7m 지점까지 이동
  관측 갱신: 주방 내부 4-뷰, front에 냉장고 전면이 크게 포착 u≈0.48, v≈0.50

[t=2] 접근
  PointNav(d=front, [u,v]=[0.48, 0.42])  # 냉장고 하단부 바닥
    → Executor가 goal radius 0.3m 안으로 진입
  goal-progress 도구: "fridge: candidate confirmed, distance≈0.4m"

[t=3] 완료 스킬(completion package)
  MLLM: 냉장고가 중앙·근접·전체 프레임 점유 → 도착 확신
  termination 도구 호출 → 루프 종료, success

이 추적이 드러내는 설계의 핵심은 MLLM이 단 한 번도 저수준 모터 명령(선속도·각속도·waypoint의 미터 좌표)을 산출하지 않는다는 점이다. MLLM의 출력은 전 구간에서 (뷰 선택, [u,v] 픽셀)라는 동일한 추상이며, 깊이 역투영·내비메시 스냅·측지 경로·추종은 모두 결정론적 Executor가 처리한다. 이것이 §3.1의 "통합 인터페이스"가 학습 없는 제로샷 일반화를 가능케 하는 메커니즘이다 — MLLM은 자신이 사전학습에서 익힌 "이미지 위 어디를 가리킬 것인가"라는 능력만 쓰면 되고, 로봇 동역학·좌표계·플랫폼 제약은 전혀 알 필요가 없다.

실패 경로의 회복(recovery package) 예시. 만약 [t=1]에서 PointNav 목표가 벽 뒤 도달 불가 지점으로 스냅되어 Executor가 200 step 내 goal radius 진입에 실패하면, goal-progress가 "no progress"를 반환하고 MLLM은 recovery 스킬로 전환한다. recovery는 (a) turning 도구로 제자리 회전해 새 시야 확보, (b) 이전에 점검하지 않은 방향의 [u,v] 재지정, (c) 반복 실패 영역을 텍스트 이력에 "dead-end"로 기록해 재방문 회피 — 를 수행한다. 즉 스킬 패키지가 유한상태기계(FSM)의 상태 전이를 자연어 지침으로 인코딩하며, OptiSight(5-상태 FSM)의 하드코딩된 전이와 달리 SuperNav는 전이 로직 자체를 MLLM 추론에 위임해 과제 유형(instance/multi/demand/OVON)에 걸쳐 재사용한다.

3.6 컨텍스트 비용 정량 분석 (Token-Budget Analysis)

§3.4의 media-only pruning이 왜 장기지평에서 결정적인지 토큰 관점에서 분석한다. GPT-5.6 Terra high가 처리하는 이미지 한 장을 대략 N_img 토큰(고해상 뷰 기준 수백~천 토큰대)이라 하면, 정리 없이 매 스텝 4-뷰를 누적할 때 스텝 T에서의 이미지 토큰 총량은:

누적(naive)     : 4 · N_img · T           # T에 선형 폭발
media-only정리  : 4 · N_img · W_recent     # W_recent = 유지 창(상수)

HM3D 과제가 최대 500 action, MCP 180초·tool 300초 예산 안에서 수십수백 스텝을 돈다는 점을 고려하면, naive 방식은 수십 스텝만에 컨텍스트 윈도를 소진하고 그 뒤로는 오래된 관측이 강제 절단되며 과제 상태(어떤 목표가 남았는지)마저 유실된다. media-only pruning의 통찰은 "서사(narrative)"와 "픽셀(pixels)"을 분리한 데 있다 — 텍스트 이력·goal records·이미지 경로는 토큰이 싸므로 전부 보존하고, 비싼 픽셀 페이로드만 "대체된(superseded)" 시점에 떨군다. 그 결과 MLLM은 "복도 끝을 봤고, 주방에 들어갔고, 냉장고를 confirm했다"는 완전한 서사적 연속성을 유지한 채 토큰은 상수 창에 묶인다. 이는 multi-object(목표 순서 보존)·demand-driven(18단계 순차)처럼 긴 상태 의존성을 요구하는 과제에서 StreamVLN류 토큰-스트리밍 정책이 0.00 SR로 붕괴하는 것과 대비된다(§5.3 Multi-object 표: StreamVLN SR 0.00 vs SuperNav+Geo 34.00).

5.2 평가 지표 (Evaluation Metrics)

  • SR (Success Rate): 성공적으로 완수한 과제 비율.
  • SPL (Success weighted by Path Length): SPL = (1/N) Σ S_i · L_i / max(L_i, P_i) — S_i=성공 지시자, L_i=최단 참조 경로, P_i=실제 실행 경로. 경로 효율을 함께 본다.
  • Instance 도달 판정: min_{v∈V_g} d_nav(p, v) < 1 m (목표 뷰포인트까지 navmesh 측지거리 1m 미만).
  • Demand-driven 채점: 로봇에서 허용 객체의 축정렬 바운딩박스까지 수평 거리 ≤ 2m, 순서대로, 객체 재사용 없이, 명시적 정지.

6. 핵심 기여점 (Key Contributions)

  1. 미세조정 없는 범용 항해 에이전트. MLLM을 항해 전용으로 미세조정하지 않고, 도구·스킬·시각-점 인터페이스를 장착해 instance/multi-object/demand-driven/category-level 과제를 단일 시스템으로 처리. 범용 추론 능력을 보존(C2)하면서 과제 일반성(C1)을 달성.

  2. 통합 시각-점 인터페이스 PointNav(d,[u,v]). 고수준 의미 결정과 저수준 기하 실행을 분리하면서도 "이미지 위의 점"이라는 사전학습 MLLM 친화적 형식으로 연결. 네 방향 뷰로 방향 전환을 암묵 처리(회전 17.56→0.41회).

  3. 교체 가능한 운동 백엔드. Geo-based(고 SPL)·Learned(저 센서요구) 두 실행기를 동일 인터페이스로 교체. 의미 결정(SR)과 운동 효율(SPL)의 깔끔한 분리를 실험적으로 입증.

  4. 항해 스킬(Markdown) + 컨텍스트 관리. search/recovery/completion 절차 지식을 가중치 아닌 텍스트로 주입, media-only pruning으로 장기지평 컨텍스트 폭발 억제.

  5. 광범위 벤치 + 실로봇. Habitat-GS·AI2-THOR Demand-Bench·HM3D-OVON·HM3Dv2에서 UniNaVid·NaVid·StreamVLN·OmniNav·SoftNav·MTU3D·AstraNav·ApexNav·MSGNav·WMNav 등 다수 대비 SR 최고, Unitree Go2 실로봇 정성 시연.

  6. 공개 코드(PRL v1.0). github.com/zju3dv/SuperNav 실행가능 저장소(core agent runtime·skills·tools·evaluation utilities, Habitat-GS/AI2-THOR 통합). 단 논문의 과제 리스트·GT·실로봇 배포·벤치 과제 데이터는 아직 미공개(roadmap 명시).

7. 구현 상세 (Implementation Details)

의사결정 MLLM:

primary   : GPT-5.6 Terra, high reasoning effort
ablation  : GPT-6 Astra (medium)   ← 교체만으로 성능 향상 확인

(이 모델 식별자는 논문 본문 표기를 그대로 옮긴 것이다.)

Geo-based Executor: standoff 0.70 m / candidate snap 0.75 m / follower goal radius 0.30 m / follower steps 200 / Recast·Detour PathFinder + GreedyGeodesicFollower.

Learned Executor: DINOv2 인코더, visual history 12(stride-2 + 현재), 변위 8×2D @0.25m, stop pt≥0.1 연속 2회, primitives 10° 회전 + 0.25m 전진.

이미지 해상도: Habitat-GS는 MLLM 입력 256×192, Habitat-Sim 시뮬레이터 640×480·90° HFOV·카메라 높이 1.25 m.

실행 한계: Codex 실행당 3,600 s / MCP 시작 180 s / 도구 호출당 300 s / HM3D 평가 액션 한계 500(베이스라인별 상이).

실로봇 매핑: 복셀 격자 0.05 m, 높이 기반 2D 통행 비용 지도.

Learned Executor 학습: 45,000 updates / batch 256 / AdamW / lr 1e-4(정책)·1e-5(백본) / wd 1e-6 / 500 warmup + cosine. 손실 ℒ_total = ℒ_flow + 0.5·ℒ_stop + 0.002·ℒ_remaining.

8. 고급 주제 (Advanced Topics)

8.1 확장성 (Scalability)

동결-MLLM 설계의 가장 큰 자산은 모델 발전의 무비용 흡수다. GPT-5.6 Terra→GPT-6 Astra 교체만으로 SR·SPL이 동반 상승했다는 아블레이션은, 미래에 더 강한 MLLM이 나오면 재학습 없이 성능이 따라 오름을 시사한다. 또한 운동 백엔드가 교체 가능하므로, 새 로봇·새 센서(예: 깊이 없는 저가 플랫폼→Learned, 고정밀 LiDAR→Geo)에 맞춰 실행기만 갈아끼우면 된다.

8.2 한계점 (Limitations)

  • SPL 열위 구간. HM3Dv2 0.2m에서 SR은 ApexNav를 앞서지만 SPL(0.3338)은 뒤진다(0.3800). 에이전트 루프의 탐색·검증이 경로를 늘린다. Learned 실행기는 SPL이 특히 낮다(0.1355~0.2059).
  • 실로봇 정량 부재. Go2 시연은 정성적이며 성공률·경로 지표가 없다.
  • 긴 과제의 SR 절대값. multi-object는 34%, demand-driven은 59.5%로, 베이스라인 대비 압도적이나 절대 성공률은 아직 낮다 — 조합적 장기지평의 본질적 난이도.
  • MLLM 호출 비용·지연. 도구 호출당 300s 한계·Codex 3,600s 등은 실시간성 제약을 드러낸다.
  • 데이터 부분 공개. 과제 리스트·GT·실로봇 코드·벤치 과제 데이터는 roadmap상 미공개로, 완전 재현에는 제약이 있다.

8.3 향후 방향 (Future Directions)

운동 백엔드의 혼합(상황별 Geo/Learned 자동 선택), 스킬 라이브러리의 자동 확장(실패 로그로부터 스킬 생성), SPL 개선을 위한 탐색-검증 예산 적응, 실로봇 정량 평가 프로토콜 확립이 자연스러운 다음 단계다.

9. 비교 분석 (Comparative Analysis)

9.2 장단점 분석

OptiSight 대비. 둘 다 "VLM 의미 결정 + 결정론적 기하 실행 분리"라는 동일 원리를 공유한다. 그러나 OptiSight는 단일 목표 탐색에 특화된 5-상태 FSM이고 Habitat 시뮬 전용인 반면, SuperNav는 임의 과제(demand-driven 1~8단계 포함)로 일반화하고 운동 백엔드를 교체 가능하게 하며 실로봇까지 간다. OptiSight가 "분해 원리의 최소 증명"이라면 SuperNav는 "그 원리의 범용 에이전트화"다.

PanoVLN 대비. PanoVLN의 CGE는 정책 호출 횟수를 신뢰도 예산으로 줄인다. SuperNav의 media-only pruning·goal-progress는 토큰(컨텍스트) 자체를 관리한다 — 둘은 직교하며 결합 가능(SuperNav 위에 CGE류 호출 게이팅을 얹으면 비용을 더 줄일 수 있다). PanoVLN은 R2R/RxR-CE 지시항해에 집중, SuperNav는 객체·수요 기반 과제에 집중한다.

WMNav 대비. WMNav는 world-model 호기심으로 탐색을 유도하는 ObjectNav 특화인데, SuperNav는 HM3Dv2 1m에서 86.50% > WMNav 72.20%로 앞선다. SuperNav는 명시적 world-model 없이 MLLM의 상식+스킬로 탐색을 유도한다는 점에서 접근이 다르다.

StreamVLN 대비. SuperNav의 직접 베이스라인으로, 단일 객체 13.33%·multi-object 0.00%로 조합 과제에서 붕괴한다. 이는 미세조정 end-to-end 정책의 과제 일반성 한계를 가장 선명하게 보여주며, SuperNav의 동결-MLLM+에이전트 설계의 존재 이유를 정당화한다.

SatNav 대비. SatNav의 SwiftVLN은 메모리 압축(GTC/STC)으로 장기지평을 다룬다. SuperNav의 media-only pruning은 더 단순하지만(이미지 페이로드만 제거) 텍스트 서사를 온전히 보존한다는 점에서 상보적이다.

9.3 실적용 가능성 평가

동결 MLLM + 교체 가능 운동 백엔드 구조는 실서비스 로봇에 바로 이식 가능한 형태다. 깊이·LiDAR가 있으면 Geo 실행기로 높은 SPL을, 저가 RGB 플랫폼이면 Learned 실행기로 동작한다. Go2 실로봇 시연이 시뮬→실 전이를 질적으로 입증했다. 다만 MLLM 호출 지연(도구당 300s 한계)과 실시간성, 그리고 긴 과제의 절대 SR(34~59%)은 실배치 전 개선이 필요하다. 코드가 PRL v1.0으로 학술 사용 무료라 재현·확장 장벽이 낮다(단 과제 데이터·실로봇 코드는 미공개).

9.4 연구 방향성 평가

SuperNav는 "항해를 학습 문제에서 에이전트 설계 문제로 재프레이밍"한다는 점에서 방향성이 선명하다. 미세조정 없이 MLLM 발전을 흡수하고, 스킬 Markdown으로 행동을 확장하며, 운동 백엔드를 교체하는 모듈성은 VLN 연구의 지배적 패러다임(대규모 미세조정)에 대한 강력한 대안을 제시한다. 아블레이션이 보여준 "MLLM만 교체해도 성능 상승"은 이 방향의 미래 지속성을 뒷받침한다.

11. 결론 (Conclusion)

SuperNav는 범용 서비스 항해의 과제 일반성과 장면 일반성을 미세조정 없는 에이전트 설계로 달성한다. 핵심은 세 가지다: (1) 고수준 의미 결정과 저수준 기하 실행을 잇는 통합 시각-점 인터페이스 PointNav(d,[u,v]), (2) 성능 프로파일이 다른 교체 가능한 Geo/Learned 운동 백엔드, (3) 가중치 아닌 텍스트로 절차 지식을 주입하는 항해 스킬 + media-only 컨텍스트 관리. 결과적으로 단일 시스템이 instance·multi-object·demand-driven·category-level 과제를 전부 처리하며, 미세조정 end-to-end 정책(StreamVLN multi-object 0.00%)이 붕괴하는 조합 과제에서도 34%를 유지하고, HM3Dv2 1m에서 86.50% SR로 다수 공개 베이스라인을 앞선다.

혁신성은 "항해를 학습 문제가 아니라 에이전트 오케스트레이션 문제로 재정의"한 데 있다. 이는 OptiSight가 제시한 "의미/기하 분해" 원리를 임의 과제의 범용 에이전트로 확장하고, StreamVLN류 미세조정 정책의 과제 일반성 한계를 정면으로 겨냥한다. MLLM 교체만으로 성능이 오르는 설계는 미래 모델 발전을 무비용 흡수한다는 점에서 실용적·전략적 의의가 크다.

한계는 분명하다 — 에이전트 루프의 탐색·검증이 SPL을 희생시키고(ApexNav 대비 열위), 실로봇 정량 지표가 없으며, 긴 과제의 절대 SR이 아직 낮고, MLLM 호출 지연이 실시간성을 제약하며, 과제 데이터·실로봇 코드가 미공개다. 그럼에도 PRL v1.0 공개 코드(실행가능 런타임·스킬·도구·평가 유틸)와 명료한 모듈 구조는 후속 연구의 재현·확장 장벽을 크게 낮춘다. 향후 운동 백엔드 혼합, 스킬 자동 확장, 탐색-검증 예산 적응, 실로봇 정량 평가가 이 패러다임을 성숙시킬 핵심 과제다.
