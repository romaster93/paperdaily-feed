1.2 연구 목표 (Research Objective)

OptiSight는 학습 없이(zero-shot) 실내 embodied 항해를 수행하는 하이브리드 프레임워크다. 핵심 통찰은 실내 항해가 서로 성격이 다른 두 능력 — 의미 이해(semantic understanding) 와 정밀 기하 제어(precise geometric control) — 를 동시에 요구한다는 점이며, 이 둘을 하나의 거대 모델에 뭉뚱그리지 않고 명시적으로 분리한다. 의미 추론은 Vision-Language Model(VLM)에 위임하고, 정밀 제어는 카메라 투영 기하에 기반한 결정론적 시각 서보잉(deterministic visual servoing) 으로 처리하며, 이 둘을 유한 상태 Chain-of-Thought(finite-state CoT) 아키텍처로 엮는다.

핵심 연구 질문:

"제로샷 실내 항해에서, 비용이 크고 hallucination에 취약한 VLM 호출을
 '의미적 결정이 실제로 필요한 순간(decision points)'으로만 제한하고,
 그 사이의 정밀 정렬·접근·통과는 카메라 기하로 결정론적으로 처리하면,
 8GB VRAM 예산 안에서도 신뢰성 있는 항해가 가능한가?"

기존 제로샷 VLM 기반 항해는 두 갈래로 나뉘며 각각 한계가 있다:

패러다임 대표 방법 한계
VLM 매 스텝 직접 행동 예측 ZSON, PixNav, VLM-as-policy 류 매 프레임 VLM 호출 → 지연·연산 폭증, 거리·정렬 같은 기하 추정에 취약, hallucination 누적
조밀 맵/월드모델 기반 VLFM, WMNav, frontier semantic 조밀 매핑·누적 belief map 유지 비용, 실시간·저메모리 배포 어려움

OptiSight는 이 둘 사이에서 "VLM은 갈림길에서만, 기하는 그 사이 내내" 라는 노동 분업으로 문제를 재정의한다. VLM(SEARCHING 상태)은 "목표가 있을 법한 방향/문(door)"을 고르는 의미적 판단만 담당하고, 일단 목표 후보가 잡히면 이후의 정렬(FINDING)·경로 스캔(SCANNING_PATH)·접근(NAVIGATING)·회복(RECOVERING) 은 바운딩 박스 중심과 3D 투영에 기반한 규칙 기반 제어로 처리한다. 결과적으로 조밀 맵 없이, 8GB VRAM 안에서, AI Habitat 시뮬레이터의 다양한 실내 장면에 대해 zero-shot 항해를 시연한다.

[OptiSight의 핵심 설계 철학: 의미와 기하의 분리]

전통 VLM-as-policy:
  매 프레임 → VLM("무엇을·어디로·얼마나") → 행동
  문제: VLM이 '기하(각도·거리·정렬)'까지 떠맡음 → 부정확·느림·환각

OptiSight의 분업:
  VLM (SEARCHING만)  → "저 문으로 가라" (의미적 방향 결정)
  기하 서보 (그 외 전부) → bbox center·3D 투영으로 각도/전진 결정론적 계산
  FSM(CoT)            → 두 모드를 언제 전환할지 상태 전이로 규율

이 논문은 별도의 신경망 학습이나 파인튜닝 없이, 공개된 소형 오픈웨이트 모델(Qwen VLM + SAM2.1 + GroundingDINO)의 조합과 결정론적 제어 로직만으로 항해를 구성한다는 점에서, "얼마나 큰 모델이냐"가 아니라 "언제 모델을 호출하느냐"를 설계 변수로 승격시킨 엔지니어링-중심(engineering-first) 연구다.

2. 문제 정의 (Problem Definition)

2.1 도전과제 (Challenges)

A. VLM 호출 비용과 지연

VLM을 매 프레임 호출하는 policy 방식은 개념적으로 단순하지만 실전에서 두 가지 벽에 부딪힌다.

[VLM 매 스텝 호출의 구조적 비용]

  프레임 t   → VLM 추론(수백 ms~수 초) → 행동 a_t
  프레임 t+1 → VLM 추론 ...            → 행동 a_{t+1}
  ...
  ⇒ 항해 한 에피소드에 수백~수천 회 VLM 호출
  ⇒ 실시간성 붕괴, GPU 메모리·전력 폭증
  ⇒ 저사양(8GB VRAM) 배포 불가

특히 목표를 향해 직진하며 미세 정렬하는 구간은 의미적 판단이 필요 없는데도 매 스텝 VLM을 부르는 것은 낭비다. 이 구간은 오히려 픽셀 오차 기반의 결정론적 제어가 더 정확하고 빠르다.

B. VLM의 기하 추정 취약성 (Hallucination)

VLM은 "이 방은 침실이고 저기 문이 있다" 같은 의미 판단에는 강하지만, "목표까지 몇 미터인가", "카메라 중심에서 몇 도 어긋났는가", "지금 전진하면 충돌하는가" 같은 정량적 기하 판단에는 약하다. VLM에게 각도·거리를 물으면 그럴듯하지만 틀린 값(hallucination)을 반환하고, 이 오차가 폐루프에서 누적된다.

[의미 vs 기하 — VLM의 능력 비대칭]

VLM이 잘하는 것:            VLM이 못하는 것:
  ✓ "저건 문이다"            ✗ "문까지 2.3m"
  ✓ "부엌은 오른쪽일 것"      ✗ "중심에서 7.5° 오른쪽"
  ✓ "저 방향에 목표 있음직"    ✗ "지금 전진하면 벽"

⇒ 기하는 카메라 투영·bbox로 '측정'해야지 VLM에게 '물으면' 안 됨

C. 조밀 맵/누적 belief 유지 비용

VLFM·WMNav류는 프런티어 점수나 curiosity value를 조밀 탑다운 맵에 누적한다. 이 방식은 강력하지만 (a) 맵 자료구조 유지·갱신 비용, (b) 국소화(localization) 드리프트 취약성, (c) 저메모리 환경 배포 곤란이라는 대가를 치른다. OptiSight는 조밀 맵 없이 현재 프레임의 bbox + 국소 3D 투영만으로 행동을 결정하려 한다.

D. 자원 제약(8GB VRAM) 하 신뢰성

소형 VLM(0.8B~2B)을 쓰면 메모리는 절약되지만 추론 품질이 떨어진다. 저사양에서도 신뢰성을 확보하려면 "약한 모델을 자주 부르는" 대신 "약한 모델을 결정적 순간에만, 강한 기하 제어로 둘러싸서" 부르는 구조가 필요하다.

2.2 핵심 해결책

OptiSight의 해결책은 유한 상태 기계(FSM)로 구조화된 Chain-of-Thought 로 요약된다. 항해를 5개의 명시적 상태로 분해하고, 오직 한 상태(SEARCHING)에서만 VLM을 호출하며, 나머지 상태는 전부 결정론적 시각 서보잉으로 처리한다.

[OptiSight 5-상태 CoT의 노동 분업]

  SEARCHING     ── VLM 추론(의미) ──▶ "어느 문/방향으로?" + Goal_Check(YES/NO)
  FINDING       ── Grounded-SAM ────▶ 목표 문 정밀 락온(bbox 확정)
  SCANNING_PATH ── 바닥 장애물 스캔 ─▶ 카메라 ±40° 틸트로 통행 가능성 확인
  NAVIGATING    ── 3D 투영 정렬 ────▶ waypoint까지 결정론적 접근(dist<0.30 완료)
  RECOVERING    ── 역행 로직 ───────▶ 충돌/락온 실패 시 반대 명령으로 탈출

  ⇒ VLM 호출은 SEARCHING에서만 = 갈림길에서만
  ⇒ FINDING/SCANNING/NAVIGATING은 bbox·투영 기하로 결정론적

이 구조의 이점: (1) VLM 호출 횟수가 에피소드당 수천 → 수십 회로 급감, (2) 정렬·접근의 기하가 픽셀 오차로 정확히 측정됨, (3) 조밀 맵 불필요, (4) 8GB VRAM 소형 모델로도 동작.

3. 핵심 방법론 (Core Methods)

3.1 유한 상태 Chain-of-Thought (Finite-State CoT)

OptiSight의 항해 두뇌는 codes/autonomous_navigator.py에 구현된 상태 기계다. 코드는 5개 주 상태와 2개 보조 상태를 정의한다:

# autonomous_navigator.py (핵심 상태 정의 — 코드 발췌 재구성)
self.state = "SEARCHING"   # [SEARCHING, FINDING, NAVIGATING, RECOVERING]
# 보조 상태: SCANNING_PATH, OPTICAL_SERVOING, STOPPING

각 상태의 역할과 전이 조건:

[FSM 상태 전이 다이어그램]

        ┌──────────────────────────────────────────────┐
        │                                              │
        ▼                                              │
   ┌─────────┐  Goal_Check=YES   ┌─────────┐          │
   │SEARCHING│──────────────────▶│ FINDING │          │
   │ (VLM)   │◀──────────────────│(Grounded│          │
   └─────────┘  락온 실패/재탐색   │  -SAM)  │          │
        │ Goal_Check=NO           └─────────┘          │
        │ → turn 90°                   │ 문 bbox 확정   │
        │                              ▼               │
        │                       ┌──────────────┐       │
        │                       │SCANNING_PATH │       │
        │                       │(바닥 ±40°틸트)│       │
        │                       └──────────────┘       │
        │                              │ 통행 가능      │
        │                              ▼               │
        │                       ┌────────────┐         │
        │                       │ NAVIGATING │         │
        │                       │(3D 투영정렬)│         │
        │                       └────────────┘         │
        │             충돌/투영손실     │ dist<0.30 도착 │
        │                    ┌─────────┘               │
        │                    ▼                         │
        │             ┌────────────┐  탈출 성공         │
        └─────────────│ RECOVERING │──────────────────┘
                      │(역행 로직)  │
                      └────────────┘
                        recovery≥3 → 임무 중단

이 FSM은 "생각의 사슬(chain-of-thought)"을 명시적 상태 전이로 물질화(materialize) 한다. LLM의 텍스트 CoT가 토큰 시퀀스로 추론 단계를 나열한다면, OptiSight의 CoT는 각 추론 단계를 하나의 상태로 두고, 상태마다 다른 계산 자원(VLM vs 기하 서보)을 배정한다. 이는 "언제 무거운 추론을 쓸지"를 아키텍처 수준에서 못박는 설계다.

3.2 SEARCHING 상태: VLM 의미 추론 (유일한 VLM 호출 지점)

SEARCHING은 OptiSight에서 유일하게 VLM을 호출하는 상태다. 코드상 비동기 추론 콜백으로 구현된다:

# SEARCHING 상태 — VLM 추론 (발췌 재구성)
response = await self.inference_callback(prompt)
# 구조화된 프롬프트 → <cmd>...</cmd> 태그와 Goal_Check(YES/NO) 파싱

VLM(기본 Qwen2-VL-2B, 저VRAM 모드에서 Qwen3.5-VL-0.8B)은 현재 시야를 보고:

  1. 의미적 방향 결정: "목표(문/방)가 있을 법한 방향" → <cmd> 태그로 회전/전진 명령 반환
  2. Goal_Check: 목표가 시야에 잡혔는가? YES → FINDING으로 전이, NO → 90° 회전 후 재탐색

핵심은 VLM이 각도·거리를 정량으로 내놓지 않는다는 것이다. VLM은 이산 명령(turn_left_90 등)과 YES/NO 플래그만 반환하고, 정밀 기하는 후속 상태에 넘긴다. 이것이 hallucination 노출을 최소화하는 설계 결정이다.

[SEARCHING의 VLM 프롬프트 계약(contract)]

입력:  현재 RGB 프레임 + 구조화 프롬프트(목표 설명)
출력:  <cmd>turn_left_90</cmd>  (이산 명령, 각도 값 자체는 시스템이 정의)
       Goal_Check: NO           (목표 미발견 → 회전 재탐색)

⇒ VLM은 '방향의 의미'만, '각도의 크기'는 시스템 상수로 고정
⇒ 정량 기하를 VLM에 위임하지 않음 = 환각 표면 축소

3.3 결정론적 시각 서보잉 (Deterministic Visual Servoing)

목표(문)가 잡히면 FINDING·NAVIGATING 상태는 VLM 없이 바운딩 박스 중심을 이미지 중심에 맞추는 결정론적 서보 제어를 수행한다. 핵심은 get_auto_align_command() 메서드다.

3.3.1 정규화 좌표와 오차 정의

바운딩 박스를 이미지 폭에 대해 [0, 1]로 정규화하고, 중심 0.5를 기준으로 오차를 정의한다:

# 픽셀-정렬 오차 (발췌)
error = center_x - 0.5     # 양수 = 목표가 오른쪽으로 치우침
# center_x ∈ [0,1] : bbox 중심의 정규화 x좌표

이는 카메라 투영 기하의 1차원 방위각 근사다. 정규화 x 오차는 광축에서의 방위 편차에 비례하므로, 조밀 깊이나 완전한 카메라 내부 파라미터 없이도 "어느 쪽으로 얼마나 돌아야 하는가"를 추정할 수 있다.

[bbox 중심 → 회전 방향 매핑 (카메라 투영 1D 근사)]

이미지 폭 정규화:  0.0 ─────────── 0.5 ─────────── 1.0
                  (왼쪽 끝)       (광축/중심)      (오른쪽 끝)

  center_x = 0.72  →  error = +0.22  →  "오른쪽 치우침" → turn_right
  center_x = 0.31  →  error = -0.19  →  "왼쪽 치우침"   → turn_left
  center_x ≈ 0.50  →  |error|<deadband → 정렬 완료 → move_forward

3.3.2 동적 데드밴드 (Dynamic Deadband)

핵심 참신함은 목표 거리(bbox 크기)에 따라 정렬 허용 오차를 동적으로 바꾸는 것이다. 먼 문은 작게 보이므로 픽셀 오차가 방위 오차로 과대 증폭된다 → 좁은 데드밴드로 정밀 정렬. 가까운 문은 크게 보이므로 데드밴드를 넓혀 과도한 진동(oscillation)을 막는다.

# get_auto_align_command() — 동적 데드밴드 (발췌 재구성)
if door_width < 0.3:        # 먼 문
    deadband = 0.10          # 정렬대 0.45 ~ 0.55
elif door_width < 0.6:      # 중간
    deadband = 0.08          # 정렬대 0.46 ~ 0.54 (가장 엄격)
else:                       # 가까운 문 (>0.6)
    deadband = 0.12          # 정렬대 0.44 ~ 0.56 (진동 억제)

그리고 회전 크기도 근접도에 따라 스케일한다(가까울수록 작게):

turn_multiplier = 0.25   if door_width > 0.6   # 가까움 → 작은 회전
turn_multiplier = 0.5    if 0.3 < door_width <= 0.6

이 거리-적응 게인 스케줄은 고전 시각 서보잉의 이득 스케일링(gain scheduling)을 bbox 크기라는 프록시로 근사한 것이다. 깊이 센서 없이 단안 bbox 폭만으로 근접도를 추정해 제어 게인을 조절하는, 실용적이면서 저비용인 트릭이다.

[동적 데드밴드의 물리적 직관]

먼 문 (width 0.25):   화면에서 작음 → 1px 오차 = 큰 방위각 → 좁은 데드밴드(0.10)로 정밀
가까운 문(width 0.75): 화면에서 큼 → 1px 오차 = 작은 방위각 → 넓은 데드밴드(0.12)로 진동방지
                     + 작은 turn_multiplier(0.25)로 오버슈트 방지

  ⇒ "멀 땐 정밀하게, 가까울 땐 부드럽게" — 진동 없는 수렴

3.3.3 문 통과 판정 (Door Passage)

목표 문이 화면을 가득 채우면(= 바로 앞) 통과로 판정한다:

# 문 통과 최종 판정 (발췌)
if (x_min <= 0.0 and x_max >= 1.0) or door_width > 1.2:
    # 문이 화면 좌우를 벗어남 = 문틀 안으로 진입 = 통과

정규화 bbox가 [0,1]을 넘어선다는 것은 문이 시야보다 커졌다는 뜻 — 즉 로봇이 문틀 바로 앞/안이라는 기하적 신호다. 이 역시 VLM 없이 순수 bbox 기하로 판정한다.

3.4 NAVIGATING: 3D 투영 정렬과 waypoint 도착

NAVIGATING 상태는 Habitat이 제공하는 3D 정보를 이용해 waypoint까지 접근한다:

# NAVIGATING (발췌 재구성)
if dist < 0.30:            # waypoint 도착 판정 (30cm 이내)
    # waypoint 완료 → 다음 단계
if lost_proj_count > 3:    # 3D 투영 데이터 3회 이상 손실
    # 정지 (신뢰할 수 없는 상태에서 무리한 전진 방지)

dist < 0.30(30cm)로 waypoint 완료를 판정하고, 3D 투영이 연속 3회 이상 실패하면(lost_proj_count > 3) 안전하게 정지한다. 이는 "기하 정보가 신뢰 불가능해지면 움직이지 말라"는 보수적 안전 규칙이다.

3.5 SCANNING_PATH: 바닥 장애물 스캔

주기적으로(스텝 카운터 기반) 카메라를 아래로 틸트해 바닥 통행 가능성을 확인한다:

# SCANNING_PATH 트리거 (발췌)
if self.steps_since_last_scan >= 15:   # 15스텝마다 주기 스캔
    # 카메라 ±40° 틸트 (look_down_40 / look_up_40)로 바닥 장애물 확인
    self.camera_tilted_for_obstacle = True   # 회피 중 시선 하향 유지

look_up_40으로 정면 복원, 회피 중에는 camera_tilted_for_obstacle 플래그로 시선을 하향 유지한다. 15스텝 주기 스캔은 매 스텝 바닥을 보지 않아도 되게 하여 정면 항해와 장애물 감시의 균형을 맞춘다.

3.6 RECOVERING: 역행 기반 탈출

충돌 플래그가 서거나 락온에 실패하면 RECOVERING으로 전이해 직전 명령의 반대를 실행한다:

# RECOVERING (발췌)
# 충돌 시: 부드러운 5-스텝 후진 시퀀스
# get_reverse_command(cmd): turn_left ↔ turn_right, move_forward → move_backward
self.recovery_attempts += 1
if self.recovery_attempts >= 3:
    # 3회 회복 실패 → 임무 중단(abort)

회복 시도를 3회로 제한(recovery_attempts >= 3)해 무한 루프를 방지한다. 이 역행 로직은 별도 재계획 없이 "왔던 길을 되짚어" 국소 데드락을 탈출하는 저비용 안전장치다.

    └─ FINDING/NAV: bbox 있음 → get_auto_align_command()(기하) → cmd_map → Habitat

모듈 구성 (codes/):

  • server.py — 메인 Flask 백엔드 API
  • autonomous_navigator.py — 5-상태 FSM 항해 두뇌(핵심)
  • habitat_controller.py — AI Habitat 시뮬레이터 제어(action 실행, RGB/3D 취득)
  • qwen35_bridge_server.py — Qwen VLM 추론 브리지 서버(비동기 inference_callback)
  • config.py — 모델 경로·장면·디바이스 설정
  • check_resources.py — 모델 가중치/의존성 검증

인지 스택(perception stack):

  • GroundingDINO — 개방어휘 텍스트→bbox 접지(목표 문/객체 탐지)
  • SAM2.1-hiera-tiny — 정밀 분할(FINDING에서 문 락온)
  • Qwen VLM (Qwen2-VL-2B 기본 / Qwen3.5-VL-0.8B 저VRAM) — 의미 추론(SEARCHING)

이 3개 오픈웨이트 모델은 전부 소형이며, VLM은 SEARCHING에서만 호출되므로 전체가 8GB VRAM 예산 안에 들어간다.

5.2 평가 지표 (Evaluation Metrics)

논문 초록은 "다양한 실내 시나리오에서 신뢰성 있는 zero-shot 항해"를 주장하나, arXiv 초록 발췌 범위에서는 구체적 정량 지표(SR/SPL 등) 수치가 명시되지 않았다. 표준 embodied 항해 지표(Success Rate, SPL, 충돌률, 경로 길이)가 사용될 것으로 보이나, 본 리뷰는 초록에 명시되지 않은 수치를 날조하지 않는다. 대신 코드에서 확인 가능한 동작 파라미터를 정량 근거로 제시한다.

6. 핵심 기여점 (Key Contributions)

  1. 의미-기하 분리 아키텍처의 명시적 실체화: "VLM은 의미 결정에만, 기하는 결정론적 서보에만"이라는 분업을 유한 상태 CoT로 코드 수준까지 구현. 추상적 주장이 아니라 autonomous_navigator.py의 상태 전이로 검증 가능.

  2. VLM 호출의 decision-point 국한: SEARCHING 단 하나의 상태에서만 VLM을 호출해, 매 스텝 policy 대비 VLM 호출 횟수를 수천 → 수십 회로 급감. 저비용·저지연·저환각.

  3. 거리-적응 동적 데드밴드: bbox 폭을 근접도 프록시로 삼아 정렬 데드밴드(0.080.12)와 회전 게인(0.250.5)을 거리별로 스케줄링. 깊이 센서 없이 단안 bbox만으로 진동 없는 시각 서보잉 실현.

  4. 조밀 맵 없는 항해: curiosity map/frontier map 같은 누적 자료구조 없이, 현재 프레임 bbox + 국소 3D 투영만으로 항해. 저메모리·저드리프트.

  5. 완전 공개·재현 가능 코드(MIT): Qwen VLM + SAM2.1-hiera-tiny + GroundingDINO 조합, start.py 원클릭 구동, 웹 대시보드까지 포함한 실제 동작 리포지토리 공개. 제로샷이라 학습·데이터 불필요, 8GB VRAM에서 재현 가능.

  6. 자원 제약 하 설계 원칙 제시: "큰 모델을 자주"가 아니라 "작은 모델을 결정적 순간에만 + 강한 기하 제어로 포위"라는, 엣지 배포 지향 설계 패턴을 구체 코드로 예시.

8. 고급 주제 (Advanced Topics)

8.1 확장성 (Scalability)

  • 모델 교체 용이성: config의 VLM 경로만 바꾸면 0.8B~2B 사이 모델 스왑 가능. 인지 스택(GroundingDINO/SAM2)은 개방어휘라 목표 클래스 확장이 프롬프트 수준에서 가능.
  • 상태 추가 용이성: FSM 구조라 새 행동 모드(예: 계단 오르기, 다중 목표 순회)를 상태로 추가하기 쉽다.
  • VLM 호출 예산 제어: SEARCHING 진입 빈도를 조절해 연산 예산을 명시적으로 통제 가능 — policy 방식엔 없는 장점.

8.2 한계점 (Limitations)

  1. 시뮬레이션 전용: 실기체 검증 부재. Habitat의 이상적 RGB/3D와 실제 센서 노이즈·조명 변화 사이 sim-to-real 갭 미검증.
  2. 정량 지표 부재: 초록에 SR/SPL 등 표준 지표 수치 미명시 → 다른 SOTA와의 직접 성능 비교 곤란.
  3. 문(door) 중심 설계: 상태·판정 로직이 "문 통과"에 특화(door_width, 문틀 진입 판정). 임의 객체 목표(ObjectNav 전반)로의 일반성은 코드상 문 중심 휴리스틱에 의존.
  4. 단안 bbox 근접도의 취약성: bbox 폭을 거리 프록시로 쓰므로, 부분 가림·형태 다양성이 큰 목표에서 데드밴드 스케줄이 흔들릴 수 있음.
  5. 1D 방위 근사: error = center_x - 0.5는 수평 방위만 다룸. 수직 정렬·3D 자세는 별도 3D 투영(NAVIGATING)이나 카메라 틸트에 의존.

8.3 향후 방향 (Future Directions)

  • 실기체 이식: 8GB VRAM·소형 모델 설계는 엣지 GPU(Jetson Orin 등) 실기체에 유리 → sim-to-real 검증이 자연스러운 다음 단계.
  • VLM 호출 정책 학습: "언제 SEARCHING으로 돌아갈지"를 휴리스틱 대신 경량 학습 정책으로 최적화하면 호출 예산-성공률 트레이드오프 개선 여지.
  • 일반 ObjectNav 확장: 문 중심 판정을 개방어휘 목표 일반으로 확장(GroundingDINO/SAM은 이미 개방어휘라 상태 로직만 일반화 필요).
  • 깊이 융합: 단안 bbox 근접도 대신 Habitat/센서 깊이를 데드밴드 스케줄에 직접 융합하면 정렬 견고성 향상.

9. 비교 분석 (Comparative Analysis)

OptiSight를 같은 VLN 트랙의 선행 리뷰 논문 3편과 비교한다: WMNav(VLM을 world model에 통합한 zero-shot ObjectNav, IROS 2025), LaViRA(언어-비전-로봇 3계층 분해 zero-shot VLN-CE, ICRA 2026), VLMNavBottleneck(VLM-LLM 항해의 3D 인식 병목·인식 포화 분석, ICRA 2026 WS). 세 편 모두 "VLM/제로샷 + 항해"라는 축을 공유하되, 계산 자원의 배분·기하 처리 방식이 OptiSight와 대비된다.

9.2 장단점 분석

OptiSight vs WMNav: 둘 다 VLM을 항해에 쓰지만 대척점에 있다. WMNav는 VLM 예측을 조밀 맵에 누적해 belief를 쌓는 "메모리 중심" 설계로, HM3D/MP3D에서 SOTA SR을 내지만 맵 유지·연산 비용이 크다. OptiSight는 정반대로 맵을 버리고 현재 프레임 bbox 기하로만 즉시 결정하는 "메모리 최소" 설계다. WMNav가 "무엇이 어디 있었나"를 기억해 탐색 효율을 높인다면, OptiSight는 "지금 보이는 것에 결정론적으로 정렬"해 정밀 접근·저자원을 얻는다. 탐색 커버리지는 WMNav가, 저비용 정밀 정렬·배포성은 OptiSight가 우세하다. 흥미롭게도 두 접근은 상보적이어서, WMNav의 curiosity map을 OptiSight의 SEARCHING 방향 선택에 주입하는 결합이 유망하다.

OptiSight vs LaViRA: 가장 직접적인 사상적 형제다. LaViRA도 "언어(전략)→비전(접지)→로봇(제어)"의 계층 분해로 능력을 분리하며, 이는 OptiSight의 "의미(VLM)→기하(서보)" 분리와 정확히 같은 철학이다. 차이는 (1) LaViRA는 각 계층에 서로 다른 규모의 MLLM을 배정(제어 최하층도 규칙 기반)하지만 여전히 전략·접지 단계에서 MLLM을 반복 호출하는 반면, OptiSight는 VLM을 SEARCHING 단 하나로 극단적으로 국한하고 나머지를 전부 순수 기하로 처리한다. (2) LaViRA는 실로봇(Unitree Go1, Agilex Cobot Magic) sim-to-real을 시연하고 R2R VLN-CE 정량 지표를 명시하는 반면, OptiSight는 시뮬 전용·지표 미명시다. 즉 LaViRA는 "계층 분해 + 실기체 + 정량 검증"의 완성도가, OptiSight는 "VLM 호출 최소화 + 8GB VRAM 원클릭 재현"의 경량성·배포성이 강점이다. LaViRA의 계층 분해가 더 원리적이라면, OptiSight는 그 원리를 "호출 예산"이라는 실전 축으로 밀어붙인 극단 사례다.

OptiSight vs VLMNavBottleneck: VLMNavBottleneck은 방법이 아니라 분석 논문으로, "3D 인식 정확도가 임계 이상이면 항해 성공률에 거의 기여하지 않는다(인식 포화)"를 실증하고 "항해에 실제 중요한 인식 특성"을 규명한다. 이 발견은 OptiSight의 설계 선택을 사후적으로 정당화한다 — OptiSight가 조밀·고정밀 인식 대신 거친 bbox 접지(GroundingDINO) + 결정론적 기하로도 항해가 되는 이유가 바로 인식 포화다. 즉 VLMNavBottleneck이 "왜 되는가"의 이론적 근거를, OptiSight가 "그래서 이렇게 만든다"의 구현을 제공하는 상보 관계다. 다만 VLMNavBottleneck은 코드 미공개, OptiSight는 완전 공개라는 재현성 대비가 있다.

9.3 실적용 가능성 평가

  • 엣지 배포: 8GB VRAM·소형 모델·조밀 맵 없음 → Jetson류 엣지 GPU 이식성이 비교군 중 가장 좋다. LaViRA는 실기체를 이미 보였으나 계층별 MLLM 자원이 더 크고, WMNav는 맵 유지 비용이 있다.
  • 재현성: MIT 라이선스 + start.py 원클릭 + 웹 대시보드로 진입 장벽이 가장 낮다. 학습·데이터셋 불필요(zero-shot).
  • 신뢰성 한계: 시뮬 전용·지표 미명시라 "실제 성공률"의 외부 검증이 안 된 상태. 실배포 전 SR/SPL 벤치마킹과 sim-to-real 검증이 선결 과제.
  • 적용 도메인: 현재 "문 통과" 특화라 실내 룸-투-룸 항해에 즉효. 일반 ObjectNav로 확장하려면 상태 판정의 문-중심 휴리스틱 일반화 필요.

9.4 연구 방향성 평가

OptiSight의 기술적 참신성은 새 모델·새 손실이 아니라 "계산 자원의 시간적 배분(when to call the VLM)"을 설계 변수로 승격시킨 데 있다. WMNav(메모리 배분)·LaViRA(모델 규모 배분)가 각각 "무엇을 기억할지/어떤 크기 모델을 쓸지"를 다뤘다면, OptiSight는 "언제 무거운 추론을 켤지"를 FSM으로 못박았다. 이는 VLMNavBottleneck의 인식 포화 발견과 결합하면 강력한 설계 원칙이 된다 — "인식이 포화하는 구간에선 VLM을 끄고 기하로 달려라". 향후 이 "호출 정책"을 학습으로 최적화하고, 문-중심에서 일반 목표로 확장하며, 실기체로 옮기는 것이 자연스러운 연구 궤적이다. 다만 현 시점에선 정량 검증 공백이 학술적 임팩트를 제약하며, 강점은 엔지니어링 재현성과 저자원 배포성에 있다.

11. 결론 (Conclusion)

OptiSight는 제로샷 실내 embodied 항해를 의미 추론과 기하 제어의 명시적 분업으로 재구성한다. 핵심 혁신은 새로운 신경망이 아니라, "VLM은 갈림길(SEARCHING)에서만 호출하고, 그 사이의 정렬·접근·통과·회복은 카메라 투영 기하로 결정론적으로 처리" 하는 유한 상태 CoT 아키텍처다. bbox 1D 방위 오차(center_x-0.5)와 거리-적응 동적 데드밴드(0.080.12)·게인 스케줄(0.250.5)로 깊이 센서 없이 진동 없는 시각 서보잉을 실현하고, 조밀 맵 없이 8GB VRAM 소형 모델(Qwen VLM + SAM2.1-hiera-tiny + GroundingDINO)로 동작한다.

실용적 의의는 명확하다: MIT 라이선스 + 원클릭 구동 + 학습 불필요라는 재현성, 그리고 저자원·엣지 지향 설계다. 이는 계층 분해로 실기체를 시연한 LaViRA, 메모리 누적으로 SOTA SR을 낸 WMNav와 상보적 위치를 점한다 — LaViRA/WMNav가 "성능·완성도" 축이라면 OptiSight는 "경량·배포성" 축이다. VLMNavBottleneck의 인식 포화 발견은 OptiSight의 "거친 인식 + 결정론 기하로도 충분"이라는 도박을 이론적으로 뒷받침한다.

한계도 분명하다: 시뮬 전용(실기체 미검증), 정량 지표 미명시(SOTA 직접 비교 불가), 문-중심 휴리스틱(일반 ObjectNav 일반성 제약). 따라서 향후 연구는 (1) 실기체 sim-to-real 검증과 SR/SPL 벤치마킹, (2) "언제 VLM을 켤지"의 호출 정책 학습, (3) 문 통과에서 개방어휘 일반 목표로의 확장, (4) 단안 bbox 근접도에 깊이 융합으로 나아가야 한다. 종합하면 OptiSight는 "큰 모델을 자주"가 아니라 "작은 모델을 결정적 순간에만 + 강한 기하로 포위" 라는, 자원 제약 시대의 embodied 항해 설계 패턴을 실제 동작 코드로 예시한 가치 있는 엔지니어링 기여다.
