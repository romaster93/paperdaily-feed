1.2 연구 목표 (Research Objective)

현실 세계에 배포된 VLN(Vision-Language Navigation) 로봇이 보이는 "stop-and-go"(멈추고-가기) 현상을 해결한다. 최신 VLN 시스템들은 벤치마크에서 우수한 성능을 달성하지만, 실제 로봇에 배포하면 동작과 정지를 반복하는 불연속적 운동 패턴을 보인다. 이 현상의 근본 원인은 sense-inference-execution 루프의 순차적(blocking) 처리 방식에 있다. 새로운 관측이 들어올 때마다 센싱 → 전송 → 추론이 완료될 때까지 로봇이 대기해야 하므로, 추론 비용 자체를 줄여도 불필요한 대기가 제거되지 않는다.

LiveVLN은 이 문제를 훈련 없이(training-free) 런타임 계층에서 해결한다. 핵심 아이디어는 이전 continuation을 실행하는 동안 새로운 추론을 비동기적으로 병행(overlap)하여, 동작이 연속적으로 유지되도록 하는 것이다.

2. 문제 정의 (Problem Definition)

2.1 도전과제 (Challenges)

A. Stop-and-Go 현상의 정량적 진단

논문은 Unitree G1 로봇에 NaVIDA 내비게이터를 실제 배포하여 문제를 정량화했다:

NaVIDA on Unitree G1 — 실측 진단 지표:

에피소드당 평균 대기 시간(T_wait)     : 10.64 초
에피소드 전체 시간 중 대기 비율(η_wait): 30.5%
에피소드당 정지 횟수(pause count)     : 9.25 회
에피소드당 추론 라운드(inference rounds): 9.75 회
Stop-and-go 발생 비율                : 94.9% (추론 라운드 기준)
가시 간격(visible gap, ℓ_gap)        : 평균 1.09 초
추론 왕복 시간(inference RTT)         : 평균 0.97 초

거의 모든(94.9%) 추론 라운드에서 로봇이 멈춘다. 에피소드 시간의 30% 이상이 순수 대기다.

B. 기존 접근의 한계 — "추론 속도 개선"만으로는 불충분

직관적인 해결책은 추론 속도를 높이는 것이지만, 논문은 이것이 근본 해법이 아님을 보인다:

순차적 루프의 근본 구조:

Step 1. 현재 액션 실행 완료 (T_execution)
Step 2. 새 관측 획득 (sensing)
Step 3. 서버로 전송 (transmission)
Step 4. VLM 추론 (inference)
Step 5. 다음 액션 실행 (T_execution)
...

↑ 이 루프에서 각 단계가 순차적으로 blocking하므로,
  추론 시간(Step 4)만 줄여도 Step 2, 3 대기는 남는다.

단순히 추론 주파수를 높이는 시도(High-frequency without overlap)는 오히려 대기 비율이 30.5% → 52.2%로 악화된다. 추론 요청이 쌓여 큐 대기가 늘어나기 때문이다.

C. 문제의 공식적 정의

에피소드 시간을 다음과 같이 분해한다:

T_episode = T_execution + T_wait

η_wait = T_wait / T_episode  (대기 비율, 낮을수록 좋음)

각 추론 라운드에서 5개의 타임스탬프를 정의한다:

t_send    : 관측을 서버로 전송한 시각
t_recv    : 서버로부터 continuation을 수신한 시각
t_empty   : 이전 continuation의 마지막 액션 실행 완료 시각
t_issue   : 새 continuation의 첫 액션이 발행되는 시각
t_done    : 현재 continuation의 마지막 액션 실행 완료 시각

파생 지표:

추론 레이턴시  ℓ_infer = t_recv − t_send
가시 간격     ℓ_gap   = t_issue − t_empty   (≥ 0이면 stop-and-go 발생)
실행 시간      ℓ_exec  = t_done − t_issue
추론-실행 차이 ℓ_SI    = ℓ_infer − ℓ_exec   (양수이면 추론이 실행보다 느림)

2.2 핵심 해결책

실행 스레드(Thread A)와 추론 갱신 스레드(Thread B)를 병렬로 분리하여, Thread A가 guard buffer를 실행하는 동안 Thread B가 새로운 continuation을 준비하도록 한다. 이를 Guarded Handoff with Revisable Tail 메커니즘이라 부른다. 훈련은 전혀 필요하지 않으며, 기존 사전학습된 VLM 내비게이터에 런타임 래퍼로 적용된다.

3. 핵심 방법론 (Core Methods)

3.1 3-컴포넌트 액션 상태 관리 (Three-Component Action State)

LiveVLN의 런타임은 각 시각 t에서 다음의 액션 상태를 유지한다:

q_t = [e_t | g_t | r_t]

e_t : Executed Actions    — 마지막 handoff 이후 실행 완료된 액션들
g_t : Guard Buffer        — 현재 실행 중인 committed prefix
                            (추론 완료 전까지 덮어쓸 수 없음)
r_t : Revisable Tail      — 아직 발행되지 않은 suffix
                            (새로운 추론 결과로 교체 가능)

Guard Buffer(g_t): 새 추론 라운드가 진행되는 동안 로봇이 멈추지 않고 계속 실행할 수 있는 "안전 확보 시간". 이 prefix는 committed 상태이므로 진행 중 추론이 완료되어도 교체되지 않는다.

Revisable Tail(r_t): 아직 발행되지 않은 뒷부분. 새로운 추론 결과가 도착하면 r_t를 새 continuation으로 교체한다. 이를 통해 최신 관측에 기반한 경로 수정이 가능하다.

상태 전이 다이어그램:

                 [handoff 발생]
                       ↓
  이전: q_t = [e_t | g_t | r_t]
  이후: e_{t+1} = g_t (실행 완료)
        g_{t+1} = 새 continuation의 첫 k* 액션
        r_{t+1} = 새 continuation의 나머지

3.2 Guarded Handoff 메커니즘 (Guarded Handoff Mechanism)

동시 실행 구조:

Thread A (실행 스레드):
  → g_t의 각 액션을 순서대로 로봇에 발행
  → g_t 소진 시 → 새 handoff 대기 또는 backup 실행

Thread B (갱신 스레드):
  → 가장 최신 관측 o_{t+1}을 g_t (context)와 함께 VLM에 전송
  → VLM 추론 완료 시 새 continuation û_{t+1} 반환

갱신 함수:
  û_{t+1} = D_B(o_{t+1}, g_t ; r_t)

여기서:
  o_{t+1} : 최신 시각적 관측
  g_t     : guard buffer (committed context로 추론에 활용)
  r_t     : revisable tail (새 continuation으로 교체됨)

handoff는 Thread B가 새 continuation을 반환하고, Thread A가 현재 guard buffer를 소진한 시점에 발생한다. 정확히 g_t 소진 전에 û_{t+1}이 준비되면 seamless handoff가 달성된다:

Seamless handoff 조건:
  ℓ_{t, SI} ≤ T_t^{guard}

  ℓ_{t, SI} : 현재 추론-실행 시간 차이
  T_t^{guard}: guard buffer의 총 실행 시간

이 조건이 만족되면 로봇이 멈추지 않는다.

3.3 실시간 적응적 Guard 크기 조정 (Real-Time Adaptive Guard Sizing)

Guard buffer 크기를 고정하는 것은 최적이 아니다. 추론 레이턴시는 시간에 따라 변동(네트워크 지터, 서버 부하 등)하므로, guard가 너무 짧으면 seamless handoff에 실패하고, 너무 길면 경로 수정의 적시성이 저하된다.

LiveVLN은 추론 레이턴시의 지수 이동 평균(EMA) 을 기반으로 guard 크기를 동적으로 결정한다:

# 1단계: EMA 업데이트 (추론 레이턴시 스무딩)
ℓ̃_{t+1, SI} = (1 - α) * ℓ̃_{t, SI} + α * ℓ_{t, SI}

# 2단계: 예산(budget) 계산
ψ_{t+1} = ℓ̃_{t+1, SI} + δ
# ψ : 다음 라운드를 커버하기 위해 필요한 guard 실행 시간
# δ : 안전 마진 (고정 상수)

# 3단계: guard 크기 (액션 수) 결정
k_{t+1}* = min{ k ∈ {1, ..., H_{t+1}} | T_{t+1}^(k) ≥ ψ_{t+1} }

# T_{t+1}^(k) = ∑_{i=1}^{k} τ(â_{t+1}^(i))
# τ(a) : 액션 a의 추정 실행 시간 (속도/거리 기반)

파라미터 의미:

  • α : EMA 업데이트 계수 (빠른 적응 vs 스무딩 균형)
  • δ : 안전 마진 (네트워크 지터 대비 버퍼)
  • τ(a) : 각 액션의 물리적 실행 시간 추정 (예: forward 0.5m / 속도 0.3m/s = 1.67s)

3.4 Backup 액션과 예외 처리

Guard가 소진되기 전에 새 continuation이 도착하지 못하는 경우(레이턴시 급증 등):

예외 처리 로직:

if guard 완전 소진 AND 새 continuation 미도착:
    if backup action 존재:
        → backup action 실행 (보수적 진행 유지)
    else:
        → STOP (최후 수단)

Backup action은 직전 continuation의 꼬리 부분에서 파생되거나 단순 "forward" 같은 안전한 기본 동작이다.

3.5 호환성 요구사항 (Compatibility Requirements)

LiveVLN이 적용 가능한 VLM 내비게이터의 요구 사항:

1. 다중 스텝 continuation 자동회귀적 디코딩
   (action sequence를 한 번에 여러 스텝 출력)

2. committed guard buffer를 추론 입력으로 수용
   (이전 committed actions를 context로 활용 가능)

3. 순서 있는 실행 가능 액션 시퀀스 출력
   (액션 간 의존성이 명확)

4. 액션 실행 시간 추정 τ(·) 지원
   (속도 프리미티브나 지속 시간 예측)

호환 확인된 시스템: NaVid, StreamVLN, NaVILA, Uni-NaVid, NaVIDA.

재훈련 불필요: 기존 사전학습 가중치를 완전히 유지하면서 런타임 래퍼로만 동작한다.

4. 시스템 아키텍처 (System Architecture)

4.1 전체 파이프라인

[기존 Blocking 방식 (Sequential)]
=========================================
관측(o_t) → 전송 → [VLM 추론] → continuation
                              ↓
                        [실행 완료]
                              ↓
관측(o_{t+1}) → 전송 → [VLM 추론] → ...
                ↑ (대기: ℓ_gap > 0)

에피소드 타임라인:
  ─[실행]─[       대기       ]─[실행]─[     대기      ]─
                                 ↑ stop-and-go 패턴

[LiveVLN 방식 (Overlapped)]
=========================================
Thread A (실행):  ─[g_0]─────────────[g_1]─────────────[g_2]─
                          ↗ handoff           ↗ handoff
Thread B (추론):          [infer o_0]    [infer o_1]    [infer o_2]

q_0 = [e_0 | g_0 | r_0]  →  handoff  →  q_1 = [g_0 | g_1 | r_1]
                                                  ↑ 이전 g_0가 e_1이 됨

에피소드 타임라인:
  ─[g_0]─[g_1]─[g_2]─[g_3]─[g_4]─  ← 거의 연속 동작

5.2 평가 지표 (Evaluation Metrics)

벤치마크 지표 (기존):

  • NE (Navigation Error): 최종 위치와 목표 사이의 평균 거리 (낮을수록 좋음)
  • OS (Oracle Success Rate): 최근접 경로 지점을 기준으로 한 성공률
  • SR (Success Rate): 목표 3m 이내 도달 성공률
  • SPL (Success weighted by Path Length): 경로 효율을 가중한 성공률

배포 지표 (신규 제안):

  • T_wait: 에피소드당 총 대기 시간
  • η_wait: 대기 시간 비율 = T_wait / T_episode
  • Pause count: 에피소드당 정지 횟수
  • Episode duration: 총 에피소드 소요 시간
  • ℓ_gap (visible gap): 추론 라운드당 평균 가시 간격

5.4 리얼월드 실험 (Real-World Experiments)

플랫폼: Unitree G1 휴머노이드 로봇 카메라: Intel RealSense D455f (RGB-D) 통신: Wi-Fi (지터 ≤50ms 환경) 실험 수: 각 내비게이터별 40회 (8개 지시문 × 5회 반복)

실험 결과, LiveVLN은 두 내비게이터 모두에서 현저한 동작 연속성 향상을 달성했다. 에피소드당 정지 횟수가 9.25 → 1.20 (NaVIDA)으로 87% 감소하여, 관찰자가 볼 때 로봇이 거의 쉬지 않고 이동하는 자연스러운 보행 패턴을 보였다. 에피소드 전체 소요 시간도 19.6% 단축되었다.

5.5 어블레이션 연구 (Ablation Study)

6. 핵심 기여점 (Key Contributions)

기여 1: Stop-and-Go 문제의 체계적 진단 및 정량화

기존 연구들은 VLN 성능을 SR, SPL 등 경로 품질 지표로만 평가했다. LiveVLN은 실제 배포에서의 연속성(continuity) 을 독립적인 평가 차원으로 제시하고, 5개의 타임스탬프 기반 지표(T_wait, η_wait, pause count, ℓ_gap, episode duration)를 정의하여 stop-and-go 현상을 처음으로 체계적으로 정량화했다.

이 진단 결과는 충격적이다: 최신 VLN 시스템(NaVIDA)을 실제 로봇에 배포하면 에피소드 시간의 30.5%가 순수 대기이며, 거의 모든 추론 라운드(94.9%)에서 로봇이 멈춘다.

기여 2: Guarded Handoff with Revisable Tail

실행과 추론을 분리된 스레드에서 병렬로 처리하는 아이디어 자체는 단순하지만, 이를 VLN 시스템에서 안전하고 효과적으로 구현하는 것은 비자명하다. LiveVLN의 핵심 설계인 guard buffer + revisable tail의 조합은:

  • Guard buffer: seamless handoff 보장 (로봇이 멈추지 않음)
  • Revisable tail: 경로 수정의 적시성 유지 (최신 관측 반영)

이 두 가지를 동시에 달성한다.

기여 3: EMA 기반 실시간 Guard 크기 적응

네트워크 환경은 동적으로 변화하므로 고정 guard 크기는 최적이 아니다. 지수 이동 평균으로 추론 레이턴시를 추적하고 안전 마진을 포함한 예산을 계산하여, 네트워크 상태에 따라 guard가 자동 조정된다.

기여 4: Training-Free 플러그인 설계

NaVid, StreamVLN, NaVILA, Uni-NaVid, NaVIDA 등 다양한 사전학습 VLM 내비게이터에 재훈련 없이 적용 가능하다. 이는 새로운 VLM 백본의 지속적인 발전을 즉시 활용할 수 있다는 점에서 실용적 가치가 크다.

8. 고급 주제 (Advanced Topics)

8.1 모델 예측 제어(MPC)와의 관계

LiveVLN의 guard 크기 결정 메커니즘은 Receding Horizon Control (MPC) 과 개념적으로 유사하다. MPC가 미래 예측 기반 최적 제어 입력 시퀀스의 첫 부분만 실행하고 재계획하는 것처럼, LiveVLN도 전체 continuation 중 guard 부분만 committed하고 tail을 지속적으로 갱신한다.

MPC 관점으로 LiveVLN:
  - Horizon H: continuation 길이
  - 실행 구간: guard buffer (처음 k* 액션)
  - 재계획 주기: 새 관측 도착 시
  - 적응 메커니즘: EMA 기반 레이턴시 예측

8.2 투기적 디코딩(Speculative Decoding)과의 차별성

투기적 디코딩(Leviathan et al., ICML 2023)은 작은 draft 모델로 후보를 생성하고 큰 모델이 검증하여 추론을 가속한다. LiveVLN은 추론 자체를 가속하지 않고, 실행과 추론의 병렬화를 통해 대기 시간을 제거한다. 이 두 기법은 상호 보완적이다: 투기적 디코딩으로 추론을 가속하고 LiveVLN으로 비동기 실행을 병렬화하면 더 큰 효과를 기대할 수 있다.

8.3 한계점 (Limitations)

1. 물리적 실행 시간에 의한 한계

T_episode = T_execution + T_wait

LiveVLN은 T_wait를 줄이지만 T_execution 자체를 단축할 수 없다.
빠른 로봇 속도가 더 근본적인 에피소드 단축 방법이다.
최대 이론 절약: T_wait / T_episode (예: NaVIDA의 경우 최대 30.5%)

2. Commitment의 비가역성 Guard buffer는 커밋된 이후 변경할 수 없다. 만약 guard 실행 도중 환경이 급격히 변화하면(예: 갑작스러운 장애물 출현), guard가 소진될 때까지 대응이 불가능하다. Guard 크기를 너무 크게 설정하면 이 위험이 증가한다.

3. 실험 규모의 한계 실제 로봇 실험은 40회 반복으로 통계적 신뢰도가 제한적이다. 더 다양한 환경(야외, 복잡한 실내)과 더 많은 반복 실험이 필요하다.

4. 학회 미심사 현재 arXiv 프리프린트 상태이며 동료 심사를 거치지 않았다.

8.4 향후 연구 방향

  1. 예측-제어 통합: 더 촘촘한 추론-실행 결합으로 방향 전환 응답성 향상
  2. 적응적 실행 정책: 레이턴시 급증 시 guard 소진 중 보수적 속도 감소 전략
  3. 다중 내비게이터 앙상블: 여러 VLM 내비게이터의 continuation을 병렬로 추론하여 최선 선택

9.2 장단점 분석

LiveVLN의 장점:

  1. 직교적(orthogonal) 기여: LiveVLN은 VLM 아키텍처나 훈련 데이터와 무관하게 동작하므로, 기존의 모든 아키텍처 개선(StreamVLN, NaVIDA 등)과 조합 가능하다. 이는 매우 실용적인 특성이다.

  2. 즉시 적용 가능성: 재훈련 없이 기존 시스템에 플러그인으로 적용 가능하다. 새로운 VLM 백본이 출시될 때마다 LiveVLN을 별도 적응 없이 바로 활용할 수 있다.

  3. 측정의 새로운 관점 제시: 배포 연속성 지표(T_wait, η_wait, pause count)를 일급(first-class) 평가 지표로 제안한 것은 연구 커뮤니티에 의미 있는 기여다.

LiveVLN의 단점:

  1. SR 개선 없음: LiveVLN은 경로 성능(SR, SPL)을 개선하지 않고 단순 유지한다. 연속적인 동작이 탐색 품질 향상으로 이어지는지는 현재 불명확하다.

  2. Commitment 위험: Guard buffer가 커밋된 후 환경 변화에 즉각 대응할 수 없다는 근본 한계가 있다.

  3. 복잡한 타이밍 의존성: EMA 파라미터(α, δ)의 적절한 설정이 성능에 중요하지만, 논문에서 구체적 값을 공개하지 않았다.

9.3 실적용 가능성 평가

매우 높음: LiveVLN은 VLN 연구에서 종종 무시되어온 배포 단계의 실용적 문제를 직접 해결한다. 실제 서비스 로봇 배포 시 사용자 경험의 핵심 요소인 동작 자연스러움(smooth motion)을 77% 이상 개선하는 것은 상업적으로도 의미 있다. Training-free 특성상 기존 VLN 연구의 즉시 적용 경로로 활용할 수 있다.

특히 StreamVLN과의 결합 결과(대기 시간 7.32s → 1.63s)는 ICRA 2026에서 발표된 시스템이 LiveVLN과 결합하면 더욱 실용적인 시스템이 됨을 보인다.

9.4 연구 방향성 평가

LiveVLN이 제시하는 "런타임 연속성(runtime continuity)" 연구 방향은 이전 VLN 리뷰 논문들과 완전히 직교하는 새로운 차원이다:

  • StreamVLN, NaVILA, NavDP 등은 모두 "더 나은 정책"을 학습하는 방향
  • LiveVLN은 "좋은 정책을 어떻게 더 잘 실행하는가"를 연구

이 관점은 VLN 연구가 벤치마크 성능 너머 실배포 경험으로 전환되는 시점에서 시기적절하다. 다만 현재 논문은 SR 향상 없이 배포 효율만 다루므로, 연속적 실행이 탐색 품질(장거리, 동적 환경)에 미치는 영향에 대한 추가 연구가 필요하다.

10. 심화 분석: VLN 런타임 공학의 이론적 토대 (Advanced Analysis: Theoretical Foundations of VLN Runtime Engineering)

10.1 Stop-and-Go 문제의 정보 이론적 관점

LiveVLN이 해결하는 문제를 정보 이론 관점에서 분석하면 더 깊은 이해가 가능하다.

전통적 VLN 루프의 정보 병목:

정보 흐름 분석:

1. 시각 관측 o_t ∈ R^{H×W×3}
   → 이미지 인코더 → 토큰 v_t ∈ R^{N×d}
   정보량: I(o_t) ≈ H × W × 3 × 8 bits = 수 MB

2. 언어 지시 i ∈ V^L
   → 텍스트 인코더 → 임베딩 l ∈ R^{L×d}
   정보량: L × log|V| ≈ 수백 bits

3. VLM 추론: P(a_{t+1:t+H} | v_t, l)
   → 계산 복잡도: O(N^2) attention (N = sequence length)
   → H × |A| bits 출력

핵심 불균형:
  입력 정보량 >> 출력 정보량
  입력 처리 시간 >> 출력 이용 시간

이 불균형이 stop-and-go의 근본 원인이다. 수 MB의 관측을 처리하여 수백 bits의 액션 결정을 생성하는 과정이 전체 루프를 지배한다.

LiveVLN의 정보 재활용 전략:

Guard buffer g_t는 이미 처리된 관측 o_t에서 생성된 정보를 실행 중에 "재활용"한다. 새로운 관측 o_{t+1}이 도착하기 전까지 이전 계획의 일부를 계속 실행한다. 이는 정보 이론적으로 다음을 의미한다:

I(a_t | o_t) ≈ I(a_t | o_{t-1})  (짧은 시간 간격에서)

즉: 방금 전 관측으로 결정된 액션은 현재 관측과 비슷한 정보 가치를 가짐
    → guard buffer의 커밋이 정보 손실을 최소화

이것이 revisable tail이 없이도 guard buffer만으로 벤치마크 성능이 거의 유지되는 이유다.

10.2 Guard 크기와 안전성의 트레이드오프 분석

Guard 크기 k*의 최적화는 두 가지 상충하는 목표 사이의 균형이다:

목표 1: Seamless Handoff (k* 최대화)
  → T_t^{guard} >> ℓ_infer
  → 추론 레이턴시가 아무리 길어도 로봇이 멈추지 않음
  → 그러나: 오래된 계획을 오래 실행 → 경로 적시성 저하

목표 2: 최신 계획 반영 (k* 최소화)
  → guard가 짧을수록 새 관측이 빨리 반영됨
  → 그러나: seamless handoff 실패 시 로봇이 멈춤

EMA 기반 최적화:
k* = min{ k : T^{(k)} ≥ ℓ̃_SI + δ }

이는 Jensen's inequality 관점에서 볼 수 있다:
  E[seamless handoff 성공] = P(ℓ_infer ≤ T^{guard})

EMA + 마진 δ는 lebesgue 측도 기준으로 
P(ℓ_infer > ℓ̃_SI + δ) → 매우 작음을 보장한다
(delta가 표준편차의 1-2배이면 >95% seamless handoff 보장)

실험 결과에서의 검증:

StreamVLN (고정 guard = 2 액션):
  ℓ_infer ≈ 0.52s, guard time ≈ 2.28s
  여유 = 2.28 - 0.52 = 1.76s >> 0
  → 100% seamless handoff 가능 (실험: pause count 6.75 → 0.80)

NaVIDA (동적 guard):
  ℓ_infer ≈ 0.97s, 더 변동성 높음
  EMA 적응으로 개인화된 guard 계산
  → pause count 9.25 → 1.20 (남은 0.80, 1.20은 레이턴시 급증 이벤트)

10.3 VLN 연구의 패러다임 전환: Policy Quality vs. Runtime Quality

LiveVLN이 제기하는 가장 중요한 연구 질문은 "VLN 연구가 무엇을 최적화해야 하는가?"다.

기존 패러다임 (Policy Quality 최적화):

VLN 연구의 주요 진보 타임라인:

2018: R2R 데이터셋 (Anderson et al.) — SR 22%
2020: Pre-training (Hao et al.) — SR 43%
2021: VLN-BERT (Hong et al.) — SR 57%
2022: DUET (Chen et al.) — SR 60%
2023: ETPNav (An et al.) — SR 65%
2025: NaVid, StreamVLN — SR 56-61%

모든 발전: 더 나은 모델 아키텍처, 더 많은 데이터, 더 강력한 사전학습
측정 기준: 항상 SR, SPL (정적 시뮬레이션)

새로운 패러다임 (Runtime Quality 최적화):

LiveVLN이 제안하는 새로운 지표:

η_wait    : 배포 효율성 측정
pause count: 사용자 경험 측정
ℓ_gap     : 실시간성 측정
episode time: 작업 완료 속도 측정

의미:
- SR 61%인 NaVIDA가 SR 56%인 StreamVLN보다 "더 좋은" 시스템인가?
- 만약 NaVIDA가 에피소드 시간의 30%를 정지 상태로 보낸다면?
- 사용자 관점에서는 더 느리고 어색한 로봇이 될 수 있다

이 관점 전환은 VLN 연구를 실험실 벤치마크에서 실제 배포로 연결하는 중요한 다리다.

10.4 LiveVLN과 스트리밍 LLM 추론의 비교

최근 LLM 서빙 연구에서 유사한 문제가 연구되고 있다. LiveVLN의 접근을 이 맥락에서 분석한다:

Speculative Execution (투기적 실행):

LLM 분야:
  Speculative Decoding (Leviathan et al., 2023):
    1. Draft 모델로 k개 토큰 예측
    2. Target 모델이 한 번에 k개 토큰 검증
    3. 첫 불일치까지 수용 (나머지 재생성)
    → 속도 향상: 2-3x

VLN 분야 (LiveVLN):
    1. VLM이 H개 액션 생성 (continuation)
    2. k*개 guard로 실행 (commit)
    3. 나머지 r_t는 새 관측으로 덮어씀
    → 대기 시간 감소: 73-78%

공통점: 미래를 "투기적으로" 예측하고 실행
차이점:
  - Speculative Decoding: 속도 가속 (더 빠른 토큰 생성)
  - LiveVLN: 실행 연속성 (대기 시간 제거)
  - Speculative Decoding: 확인 필요 (불일치 시 revert)
  - LiveVLN: guard는 취소 불가 (commitment)

Video Streaming과의 유사성:

비디오 스트리밍 버퍼링:
  문제: 네트워크 지연으로 재생이 멈춤
  해결: 버퍼(선재생 분량) 확보 → 끊김 없는 재생
  
LiveVLN guard buffer:
  문제: 추론 지연으로 로봇이 멈춤
  해결: 액션 버퍼(guard) 확보 → 끊김 없는 이동

차이:
  - 비디오: 버퍼 내용이 변하지 않음
  - LiveVLN: guard는 고정, tail은 갱신 가능

10.5 실제 배포 시나리오별 적용 가이드

시나리오 1: 저지연 로컬 네트워크 (Wi-Fi, RTT < 100ms)

권장 설정:
  Guard buffer: 1-2 액션 (짧게)
  δ (마진): 50ms
  이유: 추론이 빠르므로 작은 guard로 충분
  기대 효과: 99%+ seamless handoff, 경로 적시성 최대

예시: 연구실 내 로봇 (GPU 서버 Wi-Fi 연결)

시나리오 2: 변동 네트워크 (Wi-Fi + 이동, RTT 50-500ms)

권장 설정:
  Guard buffer: EMA 동적 (α=0.2, δ=200ms)
  이유: 지터가 크므로 EMA로 적응
  기대 효과: 95%+ seamless handoff

예시: 건물 내 이동 로봇 (AP 핸드오프 존재)

시나리오 3: 고지연 원격 제어 (5G/LTE, RTT 100-1000ms)

권장 설정:
  Guard buffer: 크게 (3-5 액션)
  δ (마진): 300-500ms
  이유: 지연이 크고 변동성 높음
  주의: guard가 길면 급격한 환경 변화 대응 느림

예시: 재난 구조 원격 로봇

시나리오 4: 온보드 추론 (GPU 없이 CPU만)

권장 설정:
  Guard buffer: 매우 크게 (5-10 액션)
  이유: CPU 추론은 수 초 소요
  그러나: tail이 거의 실행 전에 덮임 → revisable tail 의미 감소
  
현실적 해결책:
  소형 VLM 사용 (quantized model)
  EdgeTPU/NPU 활용
  LiveVLN은 하드웨어 가속의 보완이지 대체가 아님

GitHub 저장소(https://github.com/NIneeeeeem/LiveVLN)의 핵심 파일 분석:

# real_world_demo/agent_service_live.py (서버 측 - 가상 구조)

class LiveVLNAgent:
    def __init__(self, navigator_type="navida"):
        self.navigator = load_navigator(navigator_type)
        self.guard_buffer = deque()
        self.revisable_tail = deque()
        self.ema_latency = None
        self.alpha = 0.2  # EMA 계수
        
    def refresh_continuation(self, obs, guard_context):
        """Thread B: 새 continuation 생성"""
        t_send = time.time()
        
        # guard context와 함께 추론
        new_continuation = self.navigator.predict(
            observation=obs,
            committed_context=guard_context
        )
        
        t_recv = time.time()
        latency = t_recv - t_send
        
        # EMA 업데이트
        if self.ema_latency is None:
            self.ema_latency = latency
        else:
            self.ema_latency = (1 - self.alpha) * self.ema_latency + \
                               self.alpha * latency
        
        return new_continuation, latency
    
    def compute_guard_size(self, continuation, safety_margin=0.2):
        """EMA 기반 guard 크기 결정"""
        budget = self.ema_latency + safety_margin
        cumulative_time = 0.0
        
        for k, action in enumerate(continuation):
            cumulative_time += self.estimate_execution_time(action)
            if cumulative_time >= budget:
                return k + 1
        
        return len(continuation)  # 전체를 guard로
    
    def estimate_execution_time(self, action):
        """액션별 실행 시간 추정"""
        action_type = action['type']
        if action_type == 'forward':
            return action['distance'] / self.robot_speed
        elif action_type in ['turn_left', 'turn_right']:
            return action['angle'] / self.angular_speed
        else:  # stop
            return 0.1

# real_world_demo/real_world_vln_live.py (클라이언트 측 - 가상 구조)

class LiveVLNController:
    def __init__(self, agent_url):
        self.agent_url = agent_url
        self.guard_buffer = []
        self.revisable_tail = []
        self.executing_idx = 0
        self.lock = threading.Lock()
        
    def thread_a_execute(self):
        """Thread A: guard buffer 실행"""
        while not self.done:
            with self.lock:
                if self.executing_idx < len(self.guard_buffer):
                    action = self.guard_buffer[self.executing_idx]
                    self.executing_idx += 1
                else:
                    # guard 소진 - backup 또는 stop
                    if self.backup_action:
                        action = self.backup_action
                    else:
                        action = StopAction()
            
            self.robot.execute(action)
    
    def thread_b_refresh(self):
        """Thread B: 새 continuation 요청"""
        while not self.done:
            obs = self.camera.capture()
            
            with self.lock:
                guard_ctx = list(self.guard_buffer)
            
            new_cont, latency = self.request_continuation(obs, guard_ctx)
            guard_size = self.agent.compute_guard_size(new_cont)
            
            with self.lock:
                # handoff 수행
                self.guard_buffer = new_cont[:guard_size]
                self.revisable_tail = new_cont[guard_size:]
                self.executing_idx = 0  # 새 guard 시작

이 구조에서 Thread A와 Thread B가 lock을 통해 동기화되어 데이터 레이스를 방지하면서 비동기 실행을 달성한다.

11. 배포 지표의 미래: VLN 벤치마킹 패러다임 논의 (Future of Deployment Metrics)

11.1 현재 VLN 벤치마킹의 한계

VLN 커뮤니티가 오랫동안 사용해온 주요 벤치마크(R2R, RxR, REVERIE)는 정적 시뮬레이션 환경에서 경로 품질만을 측정한다. LiveVLN이 보여주는 것은 이 벤치마크가 실제 배포 경험의 중요한 차원을 놓치고 있다는 것이다.

현재 벤치마크의 구조적 한계:

1. 무한 처리 시간 가정
   - 시뮬레이션에서 추론 시간 = 0 (teleport 방식)
   - 실제: 추론 1-2초, 통신 0.2-1초
   - 결과: 시뮬레이션 SR 61% ≠ 실제 사용자 경험

2. 연속성 지표 부재
   - SR, SPL은 최종 도착 성공 여부만 측정
   - 중간 과정에서 얼마나 자연스럽게 이동했는지 무시

3. 실시간 환경 변화 무시
   - Matterport3D는 정적 환경 (사람, 차량 없음)
   - 실제 배포: 동적 장애물, 변화하는 조명 등

4. 배포 하드웨어 독립성
   - 벤치마크 결과가 특정 GPU/네트워크에 의존하지 않아야 함
   - 그러나 런타임 지표는 하드웨어 의존적

11.2 제안: 통합 배포 지표 프레임워크

LiveVLN의 지표를 확장하여 더 포괄적인 배포 평가 프레임워크를 제안할 수 있다:

레벨 1: 경로 품질 (기존)
  SR, SPL, NE, OS
  → 최종 목표 달성 품질

레벨 2: 배포 연속성 (LiveVLN 제안)
  η_wait, pause_count, ℓ_gap
  → 이동의 자연스러움

레벨 3: 에너지 효율 (미래 과제)
  단위 거리당 에너지 소비
  불필요한 방향 전환 횟수
  → 실제 운용 비용

레벨 4: 사용자 경험 (미래 과제)
  주관적 자연스러움 점수 (사용자 연구)
  예측 가능성 (사용자가 로봇 경로를 예측할 수 있는가)
  → 인간-로봇 상호작용 품질

LiveVLN은 레벨 2를 정량화한 첫 연구로서,
레벨 1만으로는 충분하지 않음을 설득력 있게 보여준다.

11.3 NaVIDA와의 심층 상호작용 분석

LiveVLN은 NaVIDA를 주요 기준선으로 사용한다. NaVIDA와의 관계를 더 깊이 분석한다:

NaVIDA (NaVIDA: VLN with Inverse Dynamics Augmentation):
  arXiv: 2601.18188
  핵심: 역동역학(inverse dynamics) 증강으로 더 정확한 액션 생성
  강점: R2R SR 61.4% (기준선 대비 향상)
  약점: 에피소드 시간의 30.5%가 대기

LiveVLN + NaVIDA 시너지:
  NaVIDA가 제공하는 것: 정확한 다중 스텝 continuation
  LiveVLN이 추가하는 것: 그 continuation을 끊김 없이 실행

이 조합의 의미:
  - NaVIDA의 역동역학 정보가 τ(a) 추정에도 활용 가능
    (역동역학 = 액션 실행 시간 모델에 이미 포함된 물리 정보)
  - LiveVLN guard 크기 결정이 NaVIDA 액션 타입에 최적화 가능

잠재적 공동 최적화:
  NaVIDA의 continuation 구조:
    [a_1, a_2, ..., a_H]  ← 이미 물리적으로 타당한 시퀀스
  
  LiveVLN guard selection:
    k* ← NaVIDA 제공 실행 시간 추정 τ(a_i) 활용
    → 더 정확한 guard 크기 → 더 낮은 pause rate

11.4 향후 VLN-Runtime 통합 아키텍처 전망

LiveVLN의 영향을 받아 미래 VLN 시스템이 어떻게 설계될 것인가:

미래 통합 아키텍처 (가상):

┌─────────────────────────────────────────────┐
│         VLN Foundation Model                 │
│                                              │
│  ┌──────────────────────────────────────┐   │
│  │  VLM Policy Head                     │   │
│  │  (continuation 생성, H = 8-16 스텝) │   │
│  └───────────────────┬──────────────────┘   │
│                       ↓                      │
│  ┌──────────────────────────────────────┐   │
│  │  Runtime Execution Manager           │   │
│  │  ├─ Guard Buffer 관리               │   │
│  │  ├─ EMA Latency 추적                │   │
│  │  ├─ Adaptive Guard Sizing           │   │
│  │  └─ Seamless Handoff 스케줄링       │   │
│  └───────────────────┬──────────────────┘   │
│                       ↓                      │
│  ┌──────────────────────────────────────┐   │
│  │  Physical Controller                 │   │
│  │  (속도 제어, 장애물 회피 안전망)     │   │
│  └──────────────────────────────────────┘   │
└─────────────────────────────────────────────┘

핵심 변화:
  - Runtime Manager가 Foundation Model의 표준 구성요소가 됨
  - 배포 지표(η_wait 등)가 학습 목적에 포함될 수 있음
  - 물리 제어기가 guard 실패 시 안전망으로 독립 동작

11. 결론 (Conclusion)

LiveVLN은 VLN 시스템의 배포 연속성이라는 새로운 문제를 제기하고, 실용적인 해결책을 제시한다. 기존 리뷰 논문들(StreamVLN, NaVILA, NavDP)이 "어떻게 더 좋은 경로를 계획할 것인가"에 초점을 맞춘 반면, LiveVLN은 "어떻게 계획된 경로를 더 잘 실행할 것인가"라는 직교적 관점을 제공한다.

혁신성: Stop-and-go 현상을 처음으로 체계적으로 정량화하고, 이를 런타임 설계 문제로 재정의한 것은 개념적으로 중요한 기여다. Guard buffer + revisable tail의 조합은 단순하지만 효과적이며, 77.7%의 대기 시간 감소라는 인상적인 결과를 달성했다.

실용적 의의: Training-free 플러그인으로 기존 어떤 VLM 내비게이터와도 결합 가능하며, 실제 로봇(Unitree G1)에서 검증된 결과가 있다. 서비스 로봇이나 안내 로봇처럼 사용자와 상호작용하는 시스템에서 동작의 자연스러움은 중요한 UX 요소이므로, 이 연구의 실용적 가치는 높다.

향후 연구: (1) 연속적 실행이 탐색 품질 자체에 미치는 영향 분석, (2) 동적 장애물 환경에서의 commitment 안전성, (3) edge computing 환경에서의 레이턴시 모델링 개선이 중요한 후속 과제다.
